一、设备保养任务录入页面交互优化

1. 需求背景

页面：设备保养任务录入 machine-tran-pm-task-data-entry-new（左侧保养任务列表 + 右侧保养检查表/数据录入区）。

二、需求 597：批次过站报表开发（未完成）

MES 中批次（Lot）沿工艺路线逐工序流动，每经过一个工序完成一次加工/测试，称为一次”过站”。本需求为生产/品质人员提供批次过站履历查询界面，支持按批次号、工单、工厂工单、工序、产线、进站/出站时间等维度查询，共 20 余个输出字段（含需求中途新增的初测/终测工位、BIN 分布、不良代码等）。本周完成从需求分析、后端开发到性能优化的全流程，并产出完整开发复盘文档（已存知识库《597-lot-pass-report-full-review.md》）。

**交付内容：**后端 LotYieldReportController（+127 行）与报表主 SQL（204 行，classpath 文件加载）；数据模型涉及 2 张核心事实表（lot_oper_yields、lot_oper_retests）+ 3 张 BIN/不良明细表 + 8 张维度表。

**需求纠偏（重要教训）：**一是数据源口径错误——最初误解为”在制报表”（数据源设计为 lots 表），实际是过站履历查询（应为 lot_oper_yields + lot_oper_retests），spec 评审阶段必须先与业务方对齐数据口径再谈实现；二是前端避免重复造轮子——第一版 spec 试图从零写前端页面，实际项目已有按正确规范实现的页面，最终复用前端、只补后端接口，动手前先搜索项目内是否已有实现。另有需求中途变更：新增”初测工位 + 终测工位”两列（批次在一个工序可能测试多次，第一次为初测、最后一次为终测）。

**关键设计决策：**SQL 放 classpath 文件而非 diy_services 表（service_logic 字段长度存不下 200+ 行 SQL；文件方式可版本控制、可 review、IDE 支持语法检查、随 jar 部署生效）；分页的两条 SQL（取当页数据 + count 总数）用 CompletableFuture 并行执行，耗时从两者之和降为约 max(两者)；库中时间为 YYYYMMDDHHMMSS 字符串格式（多个 BUG 的根源），统一用 to_timestamp 转换比较。

**性能优化：**索引分层策略——P0 核心单列索引（两张事实表的 lot_id、start_time、wo_id，实测建完后查询时间毫秒级）、P1 复合索引（出现明确”批次+时间”组合查询模式时再加，遵循最左前缀）、P2 覆盖索引（极致优化一般不必，维护成本高）。知识点：CREATE INDEX CONCURRENTLY 不锁表但不能在事务块内执行，IDEA 数据库工具默认包事务导致报错，改用简化版脚本。

**性能评估方法论：**渐进式压测法——用 generate_series 造数，按 1k → 1w → 10w → 50w 逐级放大，耗时线性增长（O(n)）为健康、超线性陡增说明出现瓶颈（排序落盘、JOIN 退化、统计信息失真）；必测 5 类场景：无过滤全量、仅时间范围、批次号、组合条件、深分页；用 EXPLAIN (ANALYZE, BUFFERS) 分析执行计划（Seq Scan vs Index Scan、rows 估算与实际偏差、Sort/Hash 是否超出内存落盘）；本 SQL 本质是多表 JOIN + 聚合，主导成本是参与聚合的行数。

三、本周学习

1. MES 制造执行系统

**系统定位：**MES（Manufacturing Execution System，制造执行系统）由美国先进制造研究机构 AMR 于 20 世纪 80 年代末提出，是应用在生产执行层的工业管理软件。工厂信息化五层模型：第 0 层业务（车间活动）→ 第 1 层数据采集硬件（传感器、扫描仪、RFID，现实工厂与虚拟工厂的界面）→ 第 2 层采集软件（PLC、DCS、SCADA，工站级/车间级）→ 第 3 层执行层（MES、WMS、物流系统）→ 第 4 层计划层（ERP、MRP、CRM）；MES 承上启下，需同时设计对计划层与采集层的接口，生产流程中 90% 以上的原始数据首先存在 MES。

**MES 周边系统：**EAP（设备自动化控制，给机台下指令、采集工艺特性参数与加工特性参数）；RMS（配方管理系统，卡控工艺特性参数，如上料时确认机台内菜单设置是否在 SOP 规范内）；FDC（故障侦测系统，卡控加工特性参数）；APC（先进制程控制，跨工序参数调优）；SPC（统计过程控制，计算 CP/CPK 量化过程能力）；RTD（实时派工系统，与天车、AGV 搭配）；YMS（良率管理系统，半导体行业叫法，Map 叠图分析）；QMS（质量管理系统，离散制造叫法）；WMS（仓储管理系统）。MES 需要与所有系统集成。

**MES 十一大功能模块：**数据采集、履历与历史、工作流指派、过程管理（防呆与预警）、生产调度、过程执行分析、资源管理、维修管理、人力资源管理、文档管理、计划管理。

**核心思想：**MES 的核心是对生产业务的建模——静态建模（车间、流水线、工站、设备、治具、产品的定义与勾连关系）+ 动态建模（搬运、加工、储存、检查、收料、发货六大基本活动），相当于在程序世界搭建一座”线上工厂”，物料在线上工厂的流转就相当于实际工厂的加工。它的价值定位是反映现场实时情况、警示”计划中的事情没有发生”以及”发生了哪些计划之外的情况”，而非直接提升效率、降低成本。信息化建设生命周期：流程化 → 标准化 → 信息化 → 可视化 → 数据化 → 智能化，最终目标是智能工厂。

**批次管理与生产追溯：**MES 批次管理实现生产全流程数据闭环——批次与物料、工艺、设备、人员、BOM、工单、质检全面关联，扫码/RFID 实时采集入库，追溯查询秒级定位，支持召回管理与合规报表自动生成；典型应用于食品、医药、汽车、电子制造行业。选型参考：专业 MES（用友、金蝶精益）批次管控细致，适合复杂工艺与大型制造，但开发周期长、成本高；ERP 的批次管理集中在物料/财务维度，生产过程追溯支持有限；零代码平台（简道云等）胜在灵活快速、成本低，适合业务变化快的中小制造企业。

2. SQL 优化与数据库大数据量处理

SQL 优化 15 个小技巧：

  1. 避免 select *：只查需要的列，select * 不走覆盖索引，会出现大量回表；

  2. 用 union all 代替 union：排重需要遍历、排序和比较，能不用 union 就不用；

  3. 小表驱动大表：in 适合左边大表右边小表，exists 适合左边小表右边大表；

  4. 批量操作：一次插入多值代替循环单条插入，每批控制在 500 条以内；

  5. 多用 limit：查首条加 limit 1；判断”存在”用 select 1 … limit 1 代替 count(*)；

  6. in 中值太多：业务层限制数量并分批查询；

  7. 增量查询：记录上次最大 id 和时间，每批只同步一小段数据；

  8. 高效分页：避免 limit 1000000,20 深分页（数据库要先扫过再丢弃前 100w 条），改用 where id > 上次最大 id 或 between 唯一索引定位；

  9. 用连接查询代替子查询：子查询需要创建临时表再删除，有额外性能消耗；

  10. join 的表不宜过多：阿里规范不超过 3 张，可用冗余字段代替多表关联；

  11. join 注意：inner join 时 MySQL 自动选小表驱动大表；left join 用左边的表驱动右边的表，左边要用小表；

  12. 控制索引数量：单表索引尽量 5 个以内、单个索引字段不超过 5 个，能建联合索引就不建单个索引；

  13. 选择合理的字段类型：长度固定用 char、长度可变用 varchar、金额用 decimal，能用数字类型就不用字符串；

  14. 提升 group by 效率：先用 where 缩小数据范围再分组，而不是分组后再 having 过滤；

  15. 索引优化：用 explain 查看执行计划，检查 SQL 是否命中索引、索引是否失效。

**数据库百万级数据处理：**核心观点是”100w 条数据不是决策依据，业务访问模型才是”。先做 4 个判断定位瓶颈：慢的是单条查询还是列表、是读还是写、是高峰期还是一直慢、是数据库本身还是应用层调用方式；再按顺序优化：SQL 与索引（贴合高频查询条件、联合索引最左匹配、避免索引失效）→ 深分页（改游标/主键翻页）→ 批量操作（拆小批次控制事务大小，按主键范围分段执行）→ 冷热分离（历史数据归档到历史表）→ 最后才考虑分库分表。避免 4 个误区：把慢都归因于数据量、一上来就分库分表、只盯数据库不看应用调用方式（重复查询、N+1、缓存缺失、导出直接打在线库）、优化动作没有验证闭环。
