# MySQL实战45讲 面试题精选（01-05）

## 01 基础架构：一条SQL查询语句是如何执行的？

**Q：一条 SQL 查询语句在 MySQL 内部经历了哪些模块？**

**A：** MySQL 分 Server 层和存储引擎层。流程：①连接器负责建连、认证，并在此刻读取权限（之后改权限不影响已有连接，仅对新连接生效）；②查询缓存命中直接返回（8.0 已删除）；③分析器做词法、语法分析；④优化器决定用哪个索引及多表 join 顺序；⑤执行器校验表权限后，循环调用存储引擎接口取行、过滤、返回结果。存储引擎是插件式的，负责真正的数据存取。

**Q：为什么大多数场景不建议开启查询缓存？**

**A：** 查询缓存以语句为 key、结果为 value 存内存，但只要表发生一次更新，该表所有缓存立即失效。更新压力大的库命中率极低，维护缓存反而浪费资源，弊大于利。实践上可设 query_cache_type=DEMAND 默认关闭，只对几乎不更新的静态表（如配置表）用 select SQL_CACHE ... 显式启用。MySQL 8.0 已把整块功能移除，说明社区也认定它得不偿失。

**Q：长连接和短连接怎么选？长连接的"坑"是什么？**

**A：** 建连需 TCP 握手加认证加权限加载，成本高，应尽量用长连接减少建连动作。坑：执行语句的临时内存管理在连接对象里，断开才释放；长连接长期累积会导致内存暴涨，被系统 OOM 杀掉，表现为 MySQL 异常重启。对策：①定期断开长连接，尤其是执行过大查询后；②5.7+ 可在大操作后执行 mysql_reset_connection，把连接恢复到刚建完的状态，免重连免重新鉴权。

**Q：分析器和优化器分别做什么？**

**A：** 分析器回答"你要做什么"：先词法分析识别出关键字、表名、列名，再按语法规则校验合法性；"Unknown column"这类列不存在的错误就在分析阶段报出，而不是执行阶段。优化器回答"该怎么做"：表上有多个索引时挑索引，多表 join 时定连接顺序，追求更低执行成本。记忆口诀：分析器管语句对不对，优化器管执行快不快。

**Q：无索引查询时执行器如何工作？rows_examined 是什么？**

**A：** 执行器先判对该表有无查询权限，无则报错；有则打开表，按引擎定义调用其接口：取第一行、判断 where 条件、满足则收入结果集，再循环取下一行直到表尾。慢日志的 rows_examined 统计的是执行器调用引擎接口取行的累计次数；注意执行器调一次、引擎内部可能扫多行，所以该值与引擎实际扫描行数并不完全相等。

## 02 日志系统：一条SQL更新语句是如何执行的？

**Q：redo log 的工作机制是什么？什么是 crash-safe？**

**A：** 如果每次更新都直接找磁盘对应记录再改，IO 和查找成本都太高。InnoDB 用 WAL（先写日志后写磁盘）：更新先写 redo log 并改内存即算完成，空闲时再刷回数据页。redo log 固定大小循环写，write pos 追上 checkpoint 说明满了，必须先推进 checkpoint 腾空间才能继续更新。凭这份日志，异常重启后已提交的修改都不会丢，这个能力就是 crash-safe。

**Q：redo log 和 binlog 有哪些区别？为什么要有两份日志？**

**A：** ①层次：redo log 是 InnoDB 独有；binlog 属 Server 层，所有引擎通用。②内容：redo log 是物理日志，记"某数据页做了什么物理修改"；binlog 是逻辑日志，记语句原始逻辑。③写入：redo log 固定空间循环写会覆盖；binlog 追加写，写满换文件不覆盖。历史原因：原生引擎 MyISAM 没有 crash-safe 能力，binlog 只能归档，InnoDB 作为插件引入后自带 redo log 补齐崩溃恢复。

**Q：什么是两阶段提交？不做会怎样？**

**A：** update 提交流程：执行器取行算新值交引擎→引擎写 redo log 置 prepare→执行器写 binlog→引擎把 redo log 改为 commit。目的：让两份日志的提交状态逻辑一致。反证：若先写 redo 后写 binlog，中途崩溃则原库有此更新、binlog 没有，恢复出的库少这笔；反过来则恢复库多这笔。两种顺序都会造成主备不一致，因此必须两阶段提交。

**Q：如何把库恢复到任意一秒的状态？**

**A：** 前提：定期全量备份，并完整保存期间的 binlog。步骤：①取最近一次全量备份恢复到临时库；②从备份时间点开始依次重放 binlog，重放到目标时刻（如误删表前一刻）即停，临时库即与当时线上库一致，再按需取回数据。备份越频繁，最长恢复时间（RTO）越短：一天一备最坏只补一天 binlog，一周一备要补一周，代价是更多备份存储成本。

**Q：保证数据不丢的两个关键参数是什么？**

**A：** ①innodb_flush_log_at_trx_commit=1：每次事务的 redo log 都直接持久化到磁盘，保证异常重启后已提交数据不丢；②sync_binlog=1：每次事务的 binlog 都持久化到磁盘，保证 binlog 不丢。两者都设 1 即"双 1 配置"，是最安全推荐值，代价是每次提交多一次盘上 IO，但换来 crash-safe 与主备一致性的保障。

## 03 事务隔离：为什么你改了我还看不见？

**Q：四种事务隔离级别分别是什么行为？**

**A：** 并发事务会产生脏读、不可重复读、幻读。隔离级别由低到高：①读未提交：变更未提交就能被别人看到，会脏读；②读提交：提交后才能被看到，解决脏读；③可重复读：事务内多次读取与启动时一致，InnoDB 默认级别；④串行化：读加读锁、写加写锁，冲突即等待。隔离越严效率越低，需按业务权衡；Oracle 默认读提交，从 Oracle 迁移要记得改 MySQL 的 transaction_isolation。

**Q：MVCC 是如何实现"可重复读"的？**

**A：** 核心是"视图 + 回滚日志"。每条记录更新时都附带一条回滚记录，于是同一行存在多个版本；事务启动时生成 read-view，读到对自己不可见的版本时，就沿回滚链逐级回滚，还原出自己启动时刻该看到的值。可重复读的视图在事务启动时创建、整个事务复用；读提交则是每条语句开始时新建视图；读未提交直接读最新值无视图，串行化用加锁避免并行。

**Q：为什么强烈建议避免长事务？**

**A：** 回滚日志要等"系统里没有比它更早的 read-view"时才能删除。长事务持有很老的视图，它存在期间可能访问任何数据，对应 undo log 全都得留着，导致回滚段暴涨、占用大量存储（5.5 及之前甚至文件收缩不回去），同时长期占用锁资源、阻塞别的事务，可能拖垮整库。所以业务上务必用短事务。

**Q：事务有哪几种启动方式？有什么隐性坑？**

**A：** ①显式 begin / start transaction，配 commit 或 rollback；②set autocommit=0 关闭自动提交：之后哪怕一条 select 也会隐式开启事务且不提交，直到 commit/rollback 或断连。坑：不少客户端框架默认连上就执行 set autocommit=0，长连接下会形成"意外的长事务"。建议保持 set autocommit=1，需要时显式 begin；频繁用事务可用 commit work and chain，提交并自动开启下一个事务，省掉重复 begin。

**Q：如何发现和监控长事务？**

**A：** 查 information_schema.innodb_trx，例如找执行超 60 秒的事务：select * from information_schema.innodb_trx where TIME_TO_SEC(timediff(now(),trx_started))>60。配套手段：对该表设阈值告警或 kill；测试阶段开 general_log 审计事务行为；5.6+ 可设 innodb_undo_tablespaces>=2，万一出现大事务把回滚段撑大，清理起来更方便。

**Q：可重复读有什么典型的业务适用场景？**

**A：** 数据校对/对账类逻辑。例如月末拿余额表和流水明细互相核对，需要一个"静态"的一致视图：RR 保证事务执行期间多次读取结果完全一致，不会因对账过程中其他事务提交新数据导致账目对不平。这也是"什么时候应该用可重复读"的标准答案——需要长时间稳定视图的分析型场景。

## 04 深入浅出索引（上）

**Q：哈希表、有序数组、搜索树三种索引模型各适用什么场景？**

**A：** ①哈希表：等值查询极快，但 key 无序，范围查询只能全表扫，适合 Memcached 等 KV 存储；②有序数组：等值二分、范围扫描都最优，但中间插入要挪动全部后续元素，只适合不再修改的静态数据；③搜索树：查询更新都是 O(logN)，且因索引要落盘、须控制磁盘读块次数，实际采用"N 叉树"而非二叉树——InnoDB 的 B+ 树正是因此胜出。

**Q：为什么 InnoDB 索引用 B+ 树而不是二叉树？**

**A：** 索引存在磁盘上，查询成本主要取决于读几个数据块。100 万节点的平衡二叉树高约 20，最坏要读 20 块，机械盘一次随机读约 10ms，完全不可接受。N 叉树大幅压低树高：InnoDB 整数索引单块约容纳 1200 个分叉，树高 4 即可存约 1200³≈17 亿行；根块常驻内存，第二层大概率也在内存，10 亿行的表查一个值最多约 3 次磁盘访问。

**Q：聚簇索引和二级索引有什么区别？什么是回表？**

**A：** InnoDB 是索引组织表，每个索引各对应一棵 B+ 树。主键索引（聚簇索引）叶子节点存整行数据；二级索引（非主键索引）叶子节点只存主键值。因此 select * from T where k=5 要先搜 k 树拿到主键 ID，再去主键树搜一次取整行，后一步就是回表——二级索引查询比主键查询多搜一棵树。所以应尽量用主键查询，或用覆盖索引避免回表。

**Q：为什么普遍建议使用自增主键？有没有例外？**

**A：** ①性能：自增主键每次插入都是追加写，不挪动已有记录、不触发页分裂；用无序业务字段（如身份证号）做主键，插入位置随机，可能引发页分裂，还使页利用率下降约 50%。②空间：所有二级索引叶子都存主键值，主键越小二级索引越小——整型 4 字节远优于 20 字节的字符串。例外：只有这一个索引且必须唯一的 KV 场景，可直接用业务字段做主键，省去每次回表。

**Q：什么是页分裂与页合并？带来什么影响？**

**A：** B+ 树为维持有序，插入新行时若目标数据页已满，要申请新页并把部分数据挪过去，称为页分裂；分裂使一页数据摊到两页，空间利用率约降 50%，写入性能也受损。反之，相邻页因删除导致利用率过低时会页合并，是分裂的逆过程。索引经长期删除、分裂会产生空洞，通过重建索引可让数据页重新紧凑、更省空间。

## 05 深入浅出索引（下）

**Q：什么是覆盖索引？为什么是常用优化手段？**

**A：** 若查询所需字段全部包含在某个二级索引中，如 select ID from T where k between 3 and 5，ID 本就在 k 索引叶子节点上，直接返回、无需回主键树取整行，即该索引"覆盖"了查询。回表每次都要多搜一棵主键树，覆盖索引把这些树搜索全省掉，性能提升显著。代价是为它建的联合索引占额外空间并增加维护成本，应围绕高频请求权衡是否值得。

**Q：最左前缀原则是什么？联合索引字段顺序怎么定？**

**A：** 联合索引 (a,b) 先按 a 排序、a 相同再按 b 排序，故 where a=?、a like 'x%'、a 和 b 联合条件都能走索引；字符串索引的最左 M 个字符同理。字段顺序第一原则是复用：能通过调顺序少维护一个索引的方案优先，有了 (a,b) 就不必再单建 a。若业务还有仅按 b 的查询，(a,b) 帮不上忙，需按空间原则补一个单列索引，如 (name,age) 搭配 (age)。

**Q：什么是索引下推（ICP）？解决什么问题？**

**A：** MySQL 5.6 引入。联合索引 (name,age) 处理 name like '张%' and age=10 时，最左前缀只能用 name 定位。5.6 之前要把每条"张"姓记录都回表取出整行，再到 Server 层判断 age，回表次数多；开启索引下推后，InnoDB 在索引遍历过程中直接用索引内已含的 age 先行过滤，不满足的跳过，只对通过筛选的记录回表，显著减少回表次数。

**Q：分析一条范围查询的回表次数与扫描行数口径？**

**A：** select * from T where k between 3 and 5：在 k 树定位 k=3 后逐条向后取，命中两条就回表两次；若改 select ID 则命中覆盖索引、零回表。注意口径差异：引擎走覆盖索引时内部读了 3 条索引记录，但 Server 层只收到 2 行，MySQL 的扫描行数按 Server 层统计，因此 explain/慢日志看到的行数与引擎实际读取的索引记录数可能不同。

**Q：重建索引怎么做才合理？**

**A：** 索引因删除、页分裂产生空洞后，重建能让数据页重新紧凑、省空间。普通索引用两条 alter：drop index k 再 add index(k)，合理。但主键不能这样连做：drop primary key 和 add primary key 都会触发整表重建，两条先后执行等于重建两遍，第一条白做；正确做法是直接一条 alter table T engine=InnoDB，同时完成表和主键的重建。

## 06 全局锁和表锁：给表加个字段怎么有这么多阻碍？

**Q：为什么逻辑备份需要加全局锁？FTWRL 之外有什么替代方案？**

**A：** 备份必须保证整库处于同一个逻辑时间点，否则先备 A 表、业务再更新、后备 B 表，恢复出来的数据就自相矛盾（如余额没扣但课程已加）。做法有：①FTWRL 让全库只读，但业务停摆或主从延迟；②全 InnoDB 库用 mysqldump --single-transaction，借助 MVCC 在 RR 下拿一致性视图，期间可正常更新；③MyISAM 等不支持事务的引擎只能用 FTWRL，这也是推 InnoDB 的原因之一。

**Q：set global readonly=true 和 FTWRL 都能让库只读，为什么推荐 FTWRL？**

**A：** ①readonly 变量可能被其他逻辑占用，比如用来判断主备角色，改它影响面更大；②异常行为不同：FTWRL 后客户端异常断开会自动释放全局锁，库恢复正常读写；而 readonly 设成 true 后客户端断开不会还原，库会长期不可写，风险高得多。

**Q：表锁和 MDL 锁有什么区别？**

**A：** ①表锁由 lock tables ... read/write 显式加，既限制其他线程，也限定本线程之后只能操作这些表，主要用在不支持行锁的引擎（如 MyISAM），InnoDB 场景很少用；②MDL 是元数据锁，系统自动加：增删改查加 MDL 读锁，DDL 加 MDL 写锁。设计目的是防止查询遍历数据时表结构被改，导致结果与结构对不上。读锁之间兼容，读写、写写互斥。

**Q：给小表加个字段为什么能把整个库拖垮？如何安全地加字段？**

**A：** MDL 写锁申请后，其后所有新的 MDL 读锁请求（即普通增删改查）都会被阻塞排队。若存在长事务占着 MDL 读锁，DDL 拿不到写锁，后续读写全部堆积，加上客户端重试机制，线程迅速爆满。安全做法：①先查 information_schema.innodb_trx，停掉或 kill 长事务再 DDL；②热点表用带超时的语法拿不到写锁就放弃并重试，避免堵住业务：`ALTER TABLE t NOWAIT/WAIT n ADD COLUMN ...`。

**Q：(a,b) 是联合主键时，单列索引 c 有什么隐含效果？**

**A：** InnoDB 二级索引叶子节点存的是"索引列 + 完整主键值"，因此单列索引 (c) 实际等价于 (c,a)。推论：此时再建 (c,a) 是纯冗余索引，白占空间和维护开销；若业务确实要按 c、b 联合过滤，该补的是 (c,b)。设计索引时要把"二级索引自动携带主键"算进去，避免重复建索引。

## 07 行锁功过：怎么减少行锁对性能的影响？

**Q：什么是两阶段锁协议？对编写事务有什么指导意义？**

**A：** InnoDB 的行锁在语句执行时按需加上，但不立即释放，统一等到事务提交时才释放，这就是两阶段锁协议。因此事务中语句的先后顺序不影响持锁总时长，但影响单行的持锁时间。实践原则：把最可能发生锁冲突的操作放到事务最后。如购票事务按"记日志→扣买家余额→加影院余额"执行，影院账户这行的加锁时间最短，两个购票事务只在最后一步短暂冲突，并发度最高。

**Q：遇到死锁有哪两种处理策略？为什么不建议只靠锁超时？**

**A：** ①超时等待：由 innodb_lock_wait_timeout 控制，默认 50 秒，对在线服务太慢；设太短（如 1 秒）又会误伤普通锁等待。②主动死锁检测：innodb_deadlock_detect 默认 on，发现循环等待立即回滚链条中的某个事务，让其他事务继续，响应快，是常规选择。业务侧通常对死锁做重试即可无损恢复。

**Q：热点行更新时 CPU 接近 100% 但 TPS 很低，为什么？怎么解决？**

**A：** 每个被堵住的新事务都要判断自己的加入是否形成死锁，这是 O(n) 的检测量；n 个线程并发更新同一行，检测总量约 n²。1000 个线程就是百万量级计算，没有死锁也把 CPU 耗光。解决：①在中间件或 MySQL 内部对同一行的更新进入引擎前排队，控制并发度；②把一行拆成逻辑多行（如账户余额拆 10 条记录随机加），冲突概率降为 1/10，需注意余额可能扣减为 0 的特殊处理；③确信无死锁才可临时关检测，风险是大量超时。

**Q：为什么说行锁支持是 InnoDB 替代 MyISAM 的重要原因？**

**A：** MySQL 的行锁由存储引擎层自己实现，服务器层不提供。MyISAM 不支持行锁，并发控制只能靠表锁，同一张表同一时刻只允许一个更新，并发度极低；InnoDB 支持行锁，锁冲突细化到行，更新不同行互不阻塞，高并发写入能力远强于 MyISAM。

**Q：要删除大量历史数据，怎么做才安全？**

**A：** 分批删。一条大 delete 会长时间持有大量行锁，且构成大事务：主库事务不提交就不写 binlog，备库延迟被拉长，undo 也持续膨胀。正确姿势是单连接循环执行 delete ... limit 500 这类小批量语句，直到影响行数为 0。注意不要用多个连接并发删，那会人为制造锁冲突甚至死锁，效果适得其反。

## 08 事务到底是隔离的还是不隔离的？

**Q：MVCC 的"快照"要复制整库数据吗？它是如何秒级创建的？**

**A：** 不复制任何数据。①每个事务有严格递增的事务 ID；每次更新生成新版本并记录 row trx_id，旧版本靠 undo log 链保留，历史版本按需计算，并非物理存在；②事务启动时只记录一个数组：当前活跃（未提交）事务 ID 列表，加高水位（最大事务 ID+1），构成 read view；③可见性按 row trx_id 与视图比对：低于低水位的已提交版本可见，高于等于高水位的不可见，中间的看是否在活跃数组里。所以快照只是一小组数字，创建成本极低。

**Q：一致性读和当前读有什么区别？为什么 RR 下事务会更新到"自己看不见"的数据？**

**A：** ①普通 select 是一致性读：按快照可见性规则沿 undo log 找对自己可见的版本，不加锁；②update/delete 以及 select ... for update / lock in share mode 是当前读：必须读最新已提交版本并加锁。更新若在旧版本上做会导致其他事务的修改丢失，所以更新永远走当前读。因此 B 看不到 C 未提交的 (1,2)，但 update 仍在其基础上 +1 得 3；若 C'迟迟不提交，B 的当前读还要等它释放行锁。

**Q：可重复读（RR）和读提交（RC）在实现上的本质区别是什么？**

**A：** 区别只在一致性视图的创建时机：①RR 在事务第一次快照读时创建一次 read view，整个事务复用，所以多次读到相同结果，只承认事务启动前已提交的数据；②RC 每条语句执行前都重新创建视图，所以能及时看到其他事务新提交的数据。核心组件相同：版本链 + read view + 可见性规则。RC 下 start transaction with consistent snapshot 无意义，因为视图每语句都会重建。

**Q：begin/start transaction 是事务的真正起点吗？有什么常见误区？**

**A：** 不是。begin/start transaction 只是语法起点，一致性视图要等执行到第一条操作 InnoDB 表的快照读语句时才真正创建，之前其他事务的提交对它是可见的。想立即建立快照应显式执行 start transaction with consistent snapshot。常见误区是以为 begin 之后数据就"冻结"了，实际中间空窗期发生的提交都会被看到。

## 09 普通索引和唯一索引，应该怎么选择？

**Q：普通索引和唯一索引在查询性能上差多少？**

**A：** 几乎没差别。唯一索引命中第一条记录即返回；普通索引要多找下一条直到不满足条件。但 InnoDB 以 16KB 数据页为单位读写，命中记录时整页已在内存，多看下一条只是一次指针运算，CPU 开销可忽略；只有记录恰好在页尾需读下一页时略贵，概率极低。所以选型不必考虑查询，重点看更新。

**Q：什么是 change buffer？为什么唯一索引用不了它？**

**A：** 更新时若目标数据页不在内存，普通索引可先把变更记在 change buffer 中（可持久化），省掉读盘，之后访问该页或后台线程定期 merge 时才真正应用。唯一索引必须校验唯一性，而校验必须把目标页读入内存对比，页已在内存就直接改更快，所以 change buffer 对唯一索引完全无用。merge 触发时机：访问该页、后台定期、正常关闭。

**Q：change buffer 在什么业务模型下收益最大？什么情况下反而有害？**

**A：** ①写多读少（账单、日志类）收益最大：页写完后短期内不会被读，merge 被推迟，期间积攒大量变更，显著减少随机读盘和 buffer pool 占用；②写后立刻查询的场景有害：马上触发 merge，随机 I/O 一次没少，还平添 change buffer 维护代价，这种业务应关闭它。参数 innodb_change_buffer_max_size 控制其占 buffer pool 比例。

**Q：业务上普通索引和唯一索引到底怎么选？**

**A：** ①若业务代码已保证不重复，优先普通索引，配合 change buffer 提升写入性能，大表效果明显，机械盘上尤其显著；②若唯一性必须由数据库兜底，没得选必须建唯一索引，业务正确性优先于性能；③归档库数据已确保无冲突，可把唯一索引改普通索引提高写速。案例：某大量插入的库把普通索引改成唯一索引后，内存命中率从 99% 跌到 75%，更新全部堵住。

**Q：redo log 和 change buffer 都能提升更新性能，区别是什么？**

**A：** 两者省的都是 I/O 但方向不同：①redo log（WAL）把随机写磁盘转化为顺序写，节省的是随机写消耗；②change buffer 让更新不必先把目标页读入内存，节省的是随机读消耗。二者可叠加：目标页在内存直接改、不在内存记 change buffer，再统一写 redo log，事务即可提交，成本极低。掉电也不丢，因为 change buffer 的操作同样记入了 redo log。

## 10 MySQL为什么有时候会选错索引？

**Q：优化器选择索引的依据是什么？为什么会判断失误？**

**A：** 优化器追求最小执行代价，综合扫描行数、是否排序、是否用临时表等估算。扫描行数靠索引统计信息估算：基数（cardinality，不同值个数）通过采样统计——取 N 个数据页算不同值平均值再乘以总页数；数据变更行数超 1/M 自动重新统计。采样必有误差，且普通索引还要计入回表代价，估算偏差可能让优化器误判，放着索引不用去走全表扫描。

**Q：哪些场景容易出现索引统计信息不准？怎么修复？**

**A：** 典型的是"反复删除历史数据又插入新数据"的表：若删除时有未提交事务挡着，数据版本翻倍，索引统计严重失真，explain 的 rows 与实际差距很大，导致选错索引。修复手段是执行 `analyze table t` 重新采样统计索引信息，多数统计不准的问题可由此解决。排查入口：对比 explain 预估行数与实际扫描行数是否明显不符。

**Q：如果 analyze table 解决不了，还有哪些办法应对优化器选错索引？**

**A：** ①force index 强制指定，优化器直接采用不再评估其他候选，见效快但要改 SQL 并发版，不够敏捷；②改写 SQL 引导优化器：如把 order by b limit 1 改成 order by b,a limit 1，让两个索引都要排序，扫描行数重新成为主导因素（仅限语义等价的场景）；③新建更合适的索引，或与业务确认后删掉被误用的索引；④子查询加 limit 改变代价估算也是可用的诱导手段。

## 11 怎么给字符串字段加索引？

**Q：前缀索引的原理和代价是什么？如何选择前缀长度？**

**A：** 前缀索引只存字符串前 n 个字节，省空间，但：①前缀可能相同导致回表次数增多，需要逐行取全值比对；②无法使用覆盖索引——即使前缀已覆盖查询列，系统也无法确认信息未被截断，仍要回表。选长度看区分度：`select count(distinct left(email,n))` 对比总数 `count(distinct email)`，预设可接受损失比例（如不超 5%），在满足区分度的前缀中取最短即可。

**Q：字符串前缀区分度很差（如身份证前 6 位是地址码）时怎么办？**

**A：** 两种方法：①倒序存储：存 `reverse(id_card)` 后建前缀索引，身份证尾部无地域重复规律，后几位区分度高，查询用 `where id_card=reverse('输入')`；②hash 字段：新增整型列存 `crc32(id_card)` 并对其建索引，仅 4 字节，查询需再比对原值防哈希冲突：`where id_card_crc=crc32(?) and id_card=?`。两者都不支持范围查询。

**Q：倒序存储和 hash 字段两种方案怎么对比选型？**

**A：** ①空间：倒序不增加字段、不占额外空间；hash 需多一个整型列。②CPU：每次读写倒序要多调一次 reverse，hash 要调一次 crc32，reverse 的计算开销更小。③查询稳定性：hash 冲突概率极低，平均扫描行数接近 1，性能更稳；倒序本质仍是前缀索引，可能多扫行。此外两者都只能等值查询，业务若有范围查询需求则都不可用。

**Q：给字符串字段建索引一共有哪几种方案？各自的取舍是什么？**

**A：** ①整字段索引：无额外扫描、可用覆盖索引，但占空间大；②前缀索引：省空间，代价是可能多扫行且用不上覆盖索引；③倒序存储+前缀索引：解决头部区分度差的问题，不占额外空间、CPU 消耗小，但不支持范围查询；④hash 字段索引：4 字节定长、查询性能最稳定，但有额外存储和函数计算，同样不支持范围扫描。按字段特点与查询模式选择。

## 12 为什么我的MySQL会"抖"一下？

**Q：更新语句平时执行很快，为什么偶尔会"抖"一下明显变慢？**

**A：** 根源在 WAL 机制。更新时 InnoDB 只写内存数据页和 redo log 就返回，此时内存页与磁盘页不一致，称为"脏页"，之后必须择机刷回磁盘（flush）。"抖"的时刻通常是 SQL 撞上了刷脏页：① 查询要淘汰缓冲池中的页，淘汰的恰好是脏页，必须先刷盘才能复用；② 后台刷脏页占用了 IO 资源，挤占了正常请求。所以偶尔的抖动大概率就是 flush 在发生。

**Q：哪些场景会触发刷脏页？哪两种对性能影响最大？**

**A：** 四种场景：① redo log 写满，必须推进 checkpoint，此时所有更新被堵住，写入性能跌为 0，是 InnoDB 要极力避免的；② 内存不足需要淘汰数据页，脏页要先刷盘，属于常态；③ 系统空闲时后台主动刷；④ 正常关闭前全部刷干净。真正影响线上性能的是①②：①造成间歇性更新停摆，②若一次查询淘汰的脏页太多，响应时间会明显拉长。

**Q：InnoDB 如何控制刷脏页的速度？**

**A：** 刷盘速度参考两个因素：① 脏页比例 M，按上限参数 innodb_max_dirty_pages_pct（默认 75%）折算出 0~100 的值 F1(M)；② redo log 从 checkpoint 到当前写入点的差距 N，差距越大 F2(N) 越大。取两者较大值 R，按 innodb_io_capacity × R% 的速率刷盘。因此 innodb_io_capacity 必须按磁盘真实 IOPS 配置（可用 fio 压测），配小了刷盘跟不上产脏速度，脏页越积越多。

**Q：刷脏页时的"连坐"机制是什么？SSD 上建议怎么配？**

**A：** 刷一个脏页时，若相邻数据页也是脏页会一起刷掉，且可级联蔓延，由 innodb_flush_neighbors 控制：1 开启，0 只刷自己。该优化是为机械硬盘设计的——机械盘随机 IOPS 只有几百，把随机 IO 合并成顺序 IO 收益巨大；而 SSD 的 IOPS 不是瓶颈，连坐反而拖慢必要脏页的落盘、拉长 SQL 响应时间，建议设为 0（MySQL 8.0 默认已是 0）。同时要监控脏页比例（dirty/total），别让它长期逼近 75%。

**Q：redo log 设置过小会有什么后果？**

**A：** redo log 是环形复用的，容量太小则 write pos 很快追上 checkpoint，系统被迫频繁暂停所有更新去刷脏页、推进 checkpoint。现象是：主机磁盘压力并不大，但数据库出现周期性的性能骤降和更新停顿，WAL 把随机写变顺序写的价值完全发挥不出来。大内存实例建议直接配 4 个 1GB 的文件，别吝啬。

**Q：淘汰脏页为什么要先刷盘，而不是等读入时重放 redo log？**

**A：** 刻意的设计取舍。若采用"读盘时重放"，每次读页都要先判断是否需要应用 redo，查询路径被拖慢且逻辑复杂。刷脏保证数据页只有两种状态：内存有，那内存的就是最新正确版本；内存没有，磁盘上的就是最新正确版本。读取永远不需要恢复动作，查询性能稳定可预期。

## 13 为什么表数据删掉一半，表文件大小不变？

**Q：delete 删掉一半数据后，表文件为什么不变小？**

**A：** 因为 delete 只做标记不做回收：① 删一行只是把该位置标记为"可复用"，磁盘文件不收缩；② 整页数据删光也只是把页从 B+ 树摘下标记可复用，空间不会还给操作系统。这些标记了却没被使用的空间就是"空洞"。此外随机插入导致页分裂、更新字段（等效删旧插新）也都会产生空洞，所以经大量增删改的表文件只增不减。

**Q：记录复用与页复用有什么区别？**

**A：** 记录级复用受位置约束：删掉 id=300 的记录后，只有插入 id 落在 300~600 区间的新行才能复用这个空间；页级复用没有位置限制：整页被摘掉后可服务于任何位置的插入。另外当相邻两个页利用率都很低时，系统会把数据合并到一页，释放另一页复用。正因复用条件苛刻，空洞很难被自动填平，需要主动重建表。

**Q：如何正确收缩表空间？说说 Online DDL 重建表的流程。**

**A：** 用 alter table t engine=InnoDB 重建表消除空洞。5.6 起的 Online DDL 流程：① 建临时文件，扫描原表主键全部数据页，生成一棵紧凑的新 B+ 树写入；② 重建期间原表的增删改记入 row log；③ 临时文件生成后，把 row log 中的操作应用过去；④ 用临时文件替换原表数据文件。最耗时的拷数据阶段可并发 DML，只在起止瞬间短暂持有 MDL 写锁，业务上近似无感；超大表建议用 gh-ost 更稳妥。

**Q：Online 和 inplace 是一回事吗？**

**A：** 不是，只是重建表场景恰好重合。inplace 指操作在 InnoDB 内部完成（数据写入内部临时文件而非 server 层临时表），是"原地"操作；Online 指 DDL 期间不阻塞增删改。关系是：Online 的 DDL 一定是 inplace 的；反之不成立，如加 FULLTEXT、空间索引是 inplace 但会阻塞 DML，非 Online。另一个误区：inplace 不等于不占额外空间——重建的临时文件同样需要临时空间，1TB 的表在只剩 1.2TB 的磁盘上重建是有风险的。

**Q：alter table engine=InnoDB、analyze table、optimize table 有何区别？**

**A：** ① analyze table：只重新采样统计索引信息，不改数据，加 MDL 读锁，用于统计信息不准时；② alter table t engine=InnoDB：5.6 起默认走 Online DDL 重建（recreate+analyze），能消除空洞、收缩文件；③ optimize table 等价于重建加 analyze。收缩空间用②或③，修统计信息用①。

**Q：innodb_file_per_table 对空间回收有什么影响？**

**A：** OFF 时表数据存进系统共享表空间，即使 drop table 空间也不还给操作系统，文件只增不减；ON 时每张表一个独立 .ibd 文件，删表即可完整回收。5.6.6 起默认 ON，建议保持。

**Q：Online DDL 过程中 MDL 写锁是如何安排的？**

**A：** 先短持 MDL 写锁，开始拷数据前退化成 MDL 读锁（放行增删改查），拷完数据再升级写锁完成表替换。中间是"退化"而不是直接释放，目的是防止其他线程趁机申请 DDL 写锁，保证全程只有这一个 DDL 在执行。

## 14 count()这么慢，我该怎么办？

**Q：为什么 MyISAM 的 count(*) 瞬间返回，InnoDB 却要扫全表？**

**A：** MyISAM 把表总行数单独存在磁盘上，无 where 条件时直接读出返回；InnoDB 做不到，因为默认隔离级别是可重复读，靠 MVCC 实现——同一时刻不同事务看到的行数本就不同，每一行都要先判断对当前视图是否可见才能计数，只能逐行读出累加。加上 where 条件后 MyISAM 同样快不起来。这是为支持事务付出的必然代价。

**Q：show table status 的 TABLE_ROWS 能代替 count(*) 吗？**

**A：** 不能。TABLE_ROWS 来自索引统计的采样估算，官方文档明确误差可达 40%~50%，只可当量级参考。凡采样统计值都不精确。要准确行数只能 count(*) 实算，或由业务自己维护计数。

**Q：count(*)、count(1)、count(主键 id)、count(字段) 性能差异与原理？**

**A：** 效率从低到高：count(字段) → count(主键 id) → count(1) ≈ count(*)，建议统一用 count(*)。原理：① count(主键 id)：引擎取出 id 交 server 层累加，有解析行、拷贝字段的开销；② count(1)：引擎不取值，server 层每行放个"1"累加，最省；③ count(字段)：必须取出字段值判断 NULL，语义也不同——统计的是非 NULL 行数；④ count(*)：被优化器专门优化，不取值直接按行累加。

**Q：统计表行数的需求，用 Redis 还是数据库计数表？**

**A：** 推荐数据库计数表。Redis 方案两大缺陷：① 崩溃重启可能丢失更新；② 即使正常，改计数与插数据分属两个系统、无共同事务，并发时序下计数与"最新记录列表"必然出现瞬间不一致。放 MySQL 计数表则两难全解：业务插入与 update 计数放同一事务，InnoDB 的原子性保证不丢数据，未提交的计数修改对其他事务不可见，逻辑天然一致。并发放两个语句顺序无碍，但建议把计数表更新放事务末尾，减少热点行锁等待。

**Q：count(*) 会扫主键树吗？InnoDB 怎么选索引？**

**A：** 不会特意选主键树。任何索引遍历得到的行数都一样，优化器自动挑最小的那棵索引树遍历——普通索引树比主键索引树小（叶子只存主键值），所以无 where 条件的 count(*) 通常走最小的普通索引。体现了"逻辑等价就选代价最小路径"的优化思想。

## 15 答疑文章（一）：日志和索引相关问题

**Q：两阶段提交的不同时刻崩溃重启，MySQL 如何处理？**

**A：** 崩溃恢复规则：① redo log 里事务已完整（有 commit 标识）→ 直接提交；② 只有完整 prepare → 拿 XID 查对应 binlog 是否存在且完整：完整则提交，否则回滚。对应到时刻点：写完 redo prepare、还没写 binlog 时崩溃 → 事务回滚，主备都无此数据；binlog 写完、redo 还没 commit 时崩溃 → 事务被提交。这样保证了主库与已同步到备库的 binlog 始终一致。

**Q：redo log 和 binlog 靠什么关联？如何判断 binlog 完整？**

**A：** 两份日志有公共字段 XID，恢复时顺序扫描 redo log：有 commit 的直接提交；只有 prepare 的就持 XID 去 binlog 中查找，据此决定提交或回滚。binlog 完整性判断：statement 格式末尾有 COMMIT，row 格式末尾有 XID event；5.6.2 起还引入 binlog-checksum 校验内容，可发现磁盘损坏导致的日志中间出错。

**Q：为什么不能只用 binlog、或只用 redo log 支撑崩溃恢复？**

**A：** 只留 binlog 不行：InnoDB 用 WAL，事务写完内存和 redo log 即算完成，脏页未必落盘；redo log 记录的是数据页物理改动，能用于恢复页，binlog 是逻辑日志，没有恢复数据页的能力，崩溃会造成整页级的事务丢失。只留 redo log 也不行：它循环写，无法归档保留历史；且 MySQL 主备复制、高可用和下游异构系统（如订阅 binlog 的数仓）都依赖 binlog。两者各司其职，故需两阶段提交协调。

**Q：数据最终落盘，是 redo log 更新的还是 buffer pool 写的？**

**A：** 是 buffer pool 中的脏页直接写回数据文件，与 redo log 无关——redo log 并不记录完整数据页，只记页内改动，本身没有更新磁盘数据页的能力。redo log 只在崩溃恢复时登场：发现某页可能丢了更新，就把该页读入内存，用 redo log 重放出最新内容，使其变回脏页，之后照常走脏页刷盘流程落盘。

**Q：并发互关场景（A、B 同时关注对方）为何成不了好友？怎么设计解决？**

**A：** 根因：双方关注记录都不存在时，两边 select 都查空，各自只插入单向关注，行锁又锁不住不存在的记录，形成竞态。解法：like 表加 relation_ship 字段（1 单向、2 反向、3 互关），并约定一行只存 user_id<liker_id：用 insert ... on duplicate key update relation_ship=relation_ship|1/2 原子地占住行锁，再 select 判断 relation_ship，等于 3 就 insert ignore into friend（ignore 保证幂等）。核心是把"先查后插"改造成行锁保护下的 upsert，并发下也能正确落好友关系。

**Q：能否用"先完整写 redo log，再写 binlog"代替两阶段提交？**

**A：** 不能。redo log 写完事务即不可回滚，若接着 binlog 写失败，两份日志永久不一致：崩溃恢复后主库有这笔修改、binlog 里没有，主备恢复出的数据不同。两阶段提交的本质是给 redo 和 binlog 一个"都确认就绪、再一起提交"的协调点，与分布式事务 XA 的 prepare/commit 是同一思想。

## 16 "order by"是怎么工作的？

**Q：描述 order by 的全字段排序流程。**

**A：** 以 where city='杭州' order by name limit 1000 为例：① 初始化 sort_buffer，放入 city、name、age 三个字段；② 沿 city 索引找到满足条件的主键 id，回主键索引取整行，抽出三字段存入 sort_buffer，循环直到条件不满足；③ 在 sort_buffer 中按 name 快速排序；④ 取前 1000 行返回。explain 的 Extra 出现 Using filesort 即表示需要排序。数据量超过 sort_buffer_size 时会分成多个临时文件做外部归并排序，文件越多越慢。

**Q：什么是 rowid 排序？为什么需要两种算法？**

**A：** 当单行太长（超过 max_length_for_sort_data 阈值）时，把全字段塞进 sort_buffer 会导致内存放不了几行、临时文件暴增，于是改用 rowid 算法：sort_buffer 只放排序键和主键 id，排序完再按 id 回原表取出其余字段返回。代价是多一轮回表访问（InnoDB 下是多扫一遍 B+ 树）。设计思想是：内存够就优先全字段排序，直接从内存返回结果、避免磁盘访问；担心内存不够才退而求其次用 rowid，换来单次能排更多行。

**Q：所有 order by 都要排序吗？如何用索引避免？**

**A：** 不是。需要排序是因为取出的行天然无序。建 (city,name) 联合索引后，定位到 city='杭州' 的起点，索引内后续记录本身就按 name 递增，沿索引顺序取满 1000 条即可收工——无 filesort，也无需扫完全部 4000 行。再进一步把 age 也建入索引形成 (city,name,age)，查询字段全被索引覆盖、连回主键表都省了，Extra 显示 Using index。当然索引有维护成本，要按查询频率权衡。

**Q：sort_buffer_size 配大配小各有什么影响？**

**A：** 过小：排序数据放不下就得借助磁盘临时文件做归并排序，分片越多（number_of_tmp_files 越大）性能越差，可通过 optimizer_trace 观察确认。但也不是越大越好：sort_buffer 是每连接分配的，全局调大后高并发下内存开销会成倍放大，有 OOM 风险。一般保持默认几 MB，确有个别大排序需求时在会话级临时调大即可。

**Q：update 把字段改成和原来相同的值，InnoDB 会怎么处理？**

**A：** 认真执行：照常加锁、更新 trx_id 生成新版本，不会因"值没变"而省略动作——用两个事务争抢同一行的锁冲突实验就能验证。若设置 binlog_row_image=FULL，更新前会读出整行全部字段，系统因此有条件提前发现新值与旧值相同，但语义上仍按真实更新对待。

## 17 如何正确地显示随机消息？

**Q：order by rand() limit 3 为什么这么慢？**

**A：** explain 显示 Using temporary + Using filesort：① 先把全表 word 逐行取出、配一个随机数 R，写入内存临时表，扫 10000 行；② 再全扫临时表，把 (R, rowid) 放入 sort_buffer 排序，又扫 10000 行；③ 排完按位置取前 3 行的 word，总扫描行数 20003。它必须全表扫描加全量排序，代价与 limit 无关，表越大越慢，应避免这种写法。

**Q：内存临时表排序为什么选 rowid 算法？rowid 到底指什么？**

**A：** InnoDB 表排序优先全字段，因为回表要走 B+ 树、可能多读磁盘；而 MEMORY 引擎不是索引组织表，整表就像数组，"回表"只是按下标直接取内存，几乎没有代价。优化器没了这层顾虑，自然选单行更小的 rowid 排序以排得更多更快。rowid 的本义是"引擎唯一标识一行的信息"：有主键的 InnoDB 表即主键 id，无主键则用系统生成的 6 字节隐藏 rowid，MEMORY 表就是数组下标。

**Q：优先队列排序是什么？为什么不全用归并排序？**

**A：** 当 limit N 很小、N 行的堆装得进 sort_buffer 时，用优先队列（最大堆）：先取 N 行建堆，堆顶是当前第 N 小；之后每行与堆顶比较，更小就替换，扫完堆中恰好是最小的 N 行。归并排序则会把 10000 行全部排好序，为了 3 行排序 9997 行纯属浪费。所以只需 Top-N 且堆放得下时选优先队列；N 大到堆超出 sort_buffer，才退回外部归并。

**Q：随机取行有哪些正确做法？各有何优缺点？**

**A：** ① 算法一：取 max/min(id)，令 X=(M-N)*rand()+N，再 where id>=X limit 1。约扫 3 行、极快，但 id 空间有空洞时各行被选中概率不等，分布悬殊时近乎 bug；② 算法二：count(*) 得 C，Y=floor(C*rand())，执行 limit Y,1（limit 参数不能是变量，需 prepare 或应用层拼 SQL）。概率严格均匀，共扫 C+Y+1 行，代价远小于 order by rand()；③ 算法三（随机取 3 行）：生成三个不同的 Y，各执行一次 limit Y,1。思路核心：随机逻辑上移到应用层，数据库只负责读写数据。

**Q：内存临时表有大小上限吗？超限会怎样？**

**A：** tmp_table_size 默认 16M，内存临时表超过该值就转磁盘临时表（5.7 起引擎由 internal_tmp_disk_storage_engine 决定，默认 InnoDB），性能明显下降。order by rand() 要把全表数据连同随机列放进临时表，大表极易超限，这是它慢的重要一环。

**Q：where city in ('杭州','苏州') order by name 能靠 (city,name) 索引免排序吗？**

**A：** 不能。索引只保证"同一城市内 name 有序"，in 多个值时跨城市的数据整体不再有序，优化器仍需排序。优化思路：按城市拆成多条语句，每条都利用索引免排序取本城市的 Top-N，客户端再做归并——用"一次大排序"换"N 次小索引扫描"的经典取舍。

# MySQL实战45讲 面试题精选（18-23）

## 18 为什么这些SQL语句逻辑相同，性能却差异巨大？

**Q：为什么对索引字段使用函数（如 where month(t_modified)=7）就"用不上索引"？**

**A：** ① B+ 树快速定位依赖索引值在同一层的有序性，对字段做函数计算可能破坏这种有序性，优化器因此放弃树搜索；② 即使函数不破坏有序性（如 id+1=10000），优化器也不会自动改写，仍走全索引扫描；③ 注意它并非放弃这个索引——可能仍扫该索引（选更小的），但只是全扫而非快速定位。改法：把函数逻辑改写成字段本身的范围条件，如 `where t_modified>='2016-7-1' and t_modified<'2016-8-1'`。

**Q：MySQL 字符串和数字比较的隐式转换规则是什么？为什么 varchar 字段用数字查询会全表扫描？**

**A：** ① 规则是"字符串转数字"，可用 `select '10'>9` 验证：返回 1 即字符串转数字；② 于是 `where tradeid=110717`（tradeid 是 varchar）等价于 `where CAST(tradeid AS signed)=110717`，相当于对索引字段加了函数，树搜索失效；③ 反过来，int 字段写 `where id='83126'`，转换发生在输入参数上，不影响索引字段有序性，仍能走索引。这是判断转换方向的经典技巧。

**Q：两个表关联字段字符集不同（utf8 与 utf8mb4），为什么 join 时被驱动表索引失效？怎么解决？**

**A：** ① utf8mb4 是 utf8 的超集，比较时统一把 utf8 转成 utf8mb4；② 若被驱动表字段是 utf8，相当于在被驱动表的索引字段上套了 CONVERT 函数，走不了树搜索，只能全表扫描；③ 若转换发生在驱动表取出的值上（被驱动表是 utf8mb4），则参数侧转换，索引照常可用。解决：优先统一两表字符集；暂不能改表结构时，在 SQL 中把驱动表字段显式转成被驱动表字符集，如 `where d.tradeid=CONVERT(l.tradeid USING utf8)`。

**Q：这条原则对日常开发有什么实践建议？**

**A：** ① 避免在 where 条件的索引字段上做函数运算、类型/字符集不匹配的比较，条件写在字段本身一侧；② 优化器不会替你改写 id+1=10000 这类语句，要手动等价改写；③ 每次业务代码升级，对新出现的 SQL 执行 explain 检查执行计划，是成本低、收益高的习惯。

## 19 为什么我只查一行的语句，也执行这么慢？

**Q：select * from t where id=1 长时间不返回，可能卡在哪些环节？如何排查？**

**A：** 排查第一步是 show processlist 看状态：① Waiting for table metadata lock：有事务持/等 MDL 写锁，通过 sys.schema_table_lock_waits 找到阻塞源并 kill；② Waiting for table flush：某 flush tables 命令被长查询堵住，又堵住了后续查询；③ 到了引擎层还可能等行锁：如 `select ... lock in share mode` 遇到别的事务持有该行写锁，通过 sys.innodb_lock_waits 定位，用 KILL 连接（而非 KILL QUERY）释放锁。

**Q：为什么断开占用行锁的连接要用 KILL 连接 ID，而 KILL QUERY 无效？**

**A：** ① KILL QUERY 只是停止该线程当前正在执行的语句，但持有行锁的语句早已执行完，锁是随事务持有的，停语句去不掉锁；② KILL 连接会直接断开连接，连接断开时其未提交事务被自动回滚，行锁随之释放；③ 记住原则：锁的生命周期绑定事务，只有终结事务（提交或回滚，含断连回滚）才能放锁。

**Q：扫描行数只有 1 行，查询却要几百毫秒，可能是什么原因？**

**A：** 典型场景是一致性读遇上超长 undo 链：① 另一个事务对这行连续更新了百万次且未提交，undo log 积累了百万条版本；② 普通select是快照读，要沿 undo 链逐版本回溯百万次才得到可见值，所以极慢；③ 而 `lock in share mode` 是当前读，直接读最新已提交值，反而飞快。本质：慢查询不一定扫描行数多，长事务导致的历史版本堆积是重要诱因，务必避免长事务。

**Q：'坏查询不一定是慢查询'怎么理解？**

**A：** ① 慢查询日志按执行时间（long_query_time 阈值）记录，小表上的全表扫描可能几毫秒完成，不触发慢日志，但算法是 O(N)，数据量一大必然劣化；② 应关注 Rows_examined（扫描行数）是否符合预期，而不是只看执行时间；③ 上线前把 long_query_time 设为 0 做回归，逐条检查扫描行数，能提前暴露"未来的慢查询"。

**Q：给 varchar(10) 字段查询一个 12 字符的值会发生什么？**

**A：** MySQL 截取前 10 个字符进索引匹配，会命中大量前缀相同的记录，逐条回表取整行，再在 server 层用完整值比对——全部不相等、全部丢弃。索引白走、回表巨量，表现为查一个"不存在"的值也极慢。教训：查询值要与字段定义匹配，隐式截断会让索引低效甚至名存实亡。

## 20 幻读是什么，幻读有什么问题？

**Q：什么是幻读？快照读为什么看不到幻读？**

**A：** ① 幻读指同一事务前后两次查询同一范围，后一次读到了前一次没有的"新插入的行"；② 它只在当前读（for update / lock in share mode）下出现：普通 select 是快照读，靠 MVCC 的 ReadView 看不到别的事务插入的数据；③ 另外别的事务对已有行的修改被当前读看到，不算幻读——幻读专指新插入的行。

**Q：InnoDB 在可重复读下靠什么解决幻读？行锁为什么不够？**

**A：** ① 行锁只能锁已存在的行，而新插入的行在加锁时尚不存在，无行可锁；② 插入动作本质是往记录之间的"间隙"里放数据，所以 InnoDB 引入间隙锁锁住间隙，禁止插入；③ 行锁+间隙锁合称 next-key lock（前开后闭区间），扫描到哪就锁到哪，从而同时挡住修改和插入，保证可重复读语义及 binlog 重放的数据一致性。

**Q：间隙锁之间会互相冲突吗？这带来什么经典死锁？**

**A：** ① 不会。与间隙锁冲突的是"向该间隙插入数据"这个操作，两个事务对同一间隙加间隙锁彼此兼容；② 经典死锁：事务 A、B 都对不存在的 id=9 执行 select ... for update，各拿到间隙锁 (5,10)；随后 A 插入 id=9 被 B 的间隙锁挡住，B 插入 id=9 又被 A 挡住，互相等待形成死锁；③ 启示：间隙锁降低了并发度、增加锁分析复杂度，"先锁不存在的行再插入"的代码模式要警惕。

**Q：既然间隙锁代价大，为什么不少线上库用读提交（RC）？配置上有什么讲究？**

**A：** ① RC 下没有间隙锁（外键场景除外），且行锁在语句执行完即可释放不满足条件行的锁，锁范围更小、持有更短、并发更好；② 但 RC 不能防幻读，需把 binlog_format 设为 row，靠记录行变更（而非语句）保证主备/日志重放一致；③ 配置是否合理取决于业务是否需要可重复读，要能讲清依据，"大家都这么用"不是理由。

## 21 为什么我只改一行的语句，锁这么多？

**Q：可重复读级别下 InnoDB 的加锁规则是什么？**

**A：** 记忆口诀"两原则、两优化、一 bug"：① 原则：加锁基本单位是 next-key lock（前开后闭）；只有查找过程中访问到的对象才加锁。② 优化：唯一索引等值查询命中时退化为行锁；等值查询向右遍历且最后一个值不满足条件时，退化为间隙锁。③ bug：唯一索引范围查询会一直访问到第一个不满足条件的值才停，多锁了一个 next-key lock。

**Q："锁是加在索引上的"如何理解？lock in share mode 有什么坑？**

**A：** ① InnoDB 的行锁、间隙锁都挂在索引记录上，没走到的索引不锁；② 若查询是覆盖索引（如 select id from t where c=5 lock in share mode），只锁二级索引 c，不碰主键索引，此时别的事务仍可改该行主键上的其他字段；③ 因为系统认为 for update 意图是更新，会顺带给主键上满足条件的行加行锁，lock in share mode 则不会；④ 想真正防更新，需在 select 列表中加入索引未覆盖的字段，绕开覆盖索引优化。

**Q：delete 加 limit 对加锁范围有什么影响？为什么建议删除都带 limit？**

**A：** ① 等值删除时，非唯一索引可能命中多行，不带 limit 会继续向右遍历确认，多锁住后面的间隙；② 加 limit 2 后满足条数即停，锁范围提前截止，后续间隙不再加锁，其他事务可正常插入；③ 因此删除数据尽量带 limit：既控制删除条数更安全，又缩小锁范围、减少对并发的阻塞。

**Q：next-key lock 在执行时是一次加上吗？读提交下有什么不同？**

**A：** ① 分析时当作整体，实际分两步执行：先加间隙锁，再加行锁，两步之间可能被打断；② 例如 A 持有 next-key lock (5,10] 的读锁部分，B 加锁时先成功拿到间隙锁 (5,10)，再等 c=10 的行锁；此时 A 插入 (8,8,8) 被 B 的间隙锁挡住，形成死锁；③ RC 隔离级别下没有间隙锁，next-key 退化为纯行锁，且语句执行完就释放不满足条件行的锁——这也是 RC 并发更好的原因。

**Q：非唯一索引上值相同的记录之间还有间隙吗？**

**A：** 有。非唯一索引的实际排序键是（索引列值+主键值），值相同的多条记录按主键递增排开，彼此之间同样存在间隙，也能被间隙锁锁住。加锁分析时不能把"值相同"当成连成一片，要按（值,主键）的粒度逐段分析。

## 22 MySQL有哪些"饮鸩止渴"提高性能的方法？

**Q：短连接风暴导致 Too many connections，为什么不该直接调大 max_connections？该怎么办？**

**A：** ① max_connections 的设计目的是保护 MySQL，调大后更多连接涌入，资源耗在连接和权限验证上，已连接线程抢不到 CPU，反而更糟；② 正确做法是优先 kill connection 踢掉空闲连接：查 information_schema.innodb_trx 区分，先踢事务外空闲的（Sleep 且不在事务中），再考虑事务内空闲的；③ 也可让客户端改用连接池减少建连开销；skip-grant-tables 跳过权限验证风险极高（8.0 会连带强制 skip-networking），万不得已不用。

**Q：高峰期出现慢查询压垮数据库，三类原因和对应应急方案是什么？**

**A：** ① 索引没建好：5.6+ 支持 Online DDL，紧急直接 alter table 加索引；更稳妥可备库先建（set sql_log_bin=off）再主备切换；② SQL 写得差（如字段套函数用不上索引）：MySQL 5.7 的 query_rewrite 功能在线改写语句；③ 优化器选错索引：用 force index，同样可经查询重写注入。前两类占绝大多数，且都能通过上线前回归避免。

**Q：QPS 突增把数据库打满，从数据库端有哪些止血手段？**

**A：** ① 最理想是业务侧下线问题功能；② 若新功能用独立账号，直接删除该账号并断开其连接，QPS 归零；③ 若功能与主业务同账号，可用查询重写把高危语句改写为 select 1，但风险高：可能误伤共用该模板的其他功能，且下游业务逻辑拿到假结果会连锁失败，是优先级最低的最后手段。根本之道是白名单、账号分离等规范运维体系。

**Q：如何在上生产前就拦住这类慢查询？**

**A：** ① 测试环境打开慢查询日志并把 long_query_time 设为 0，让所有语句都留痕；② 按线上量级造数，做一轮回归；③ 逐条核对 Rows_examined 是否符合预期，异常即排查；④ 新项目或改了表结构时做全量回归，可配合 pt-query-digest 等工具分析。上线前多花的时间，远少于故障复盘的时间。

**Q：为什么说建一堆单列索引可能是个坑？**

**A：** 多条件查询时优化器可能选 index merge（索引合并）：分别扫几个单列索引再取交集或并集，扫描与合并的开销往往比一个好索引大得多，效率不稳定。与其堆单列索引，不如按高频查询模式建联合索引，让一条索引完成过滤。

**Q：数据库压力已经打满，重启实例能缓解吗？**

**A：** 基本无用甚至更糟：重启后请求马上打回来，压力依旧；buffer pool 被清空，重启后相当一段时间命中率极低，等于雪上加霜。正确做法是先限流/降级保命，再定位根因（缺索引、大查询、大事务等）对症处理。

## 23 MySQL是怎么保证数据不丢的？

**Q：binlog 的写入机制是怎样的？sync_binlog 各取值意味着什么？**

**A：** ① 事务执行中日志先写线程私有的 binlog cache（大小由 binlog_cache_size 控制，超了落盘暂存），提交时一次性整体写入 binlog 文件——一个事务的 binlog 不允许拆开；② write 只是写到文件系统 page cache，fsync 才真正持久化、占磁盘 IOPS；③ sync_binlog=0 只 write 不 fsync；=1 每次提交都 fsync；=N 攒 N 个事务才 fsync，掉电最多丢最近 N 个事务的 binlog，常见取 100~1000。

**Q：redo log 有哪三种状态？innodb_flush_log_at_trx_commit 如何控制？**

**A：** 三种状态：redo log buffer（进程内存）→ write 到 page cache → fsync 到磁盘。参数取值：① 0：提交时只留在 buffer，MySQL 自身崩溃也可能丢；② 1：每次提交直接 fsync，最安全；③ 2：提交时 write 到 page cache，MySQL 崩溃不丢、主机掉电才丢。另有后台线程每秒刷盘、buffer 过半主动 write、其他事务提交时"搭便车"fsync 三种时机，所以未提交事务的 redo log 也可能已落盘。实践中建议 2 而非 0，性能接近但更安全。

**Q：什么是"双 1"配置？既然每次提交要刷两次盘，为什么 TPS 还能很高？**

**A：** ① "双 1"指 sync_binlog=1 且 innodb_flush_log_at_trx_commit=1，事务提交前 redo log（prepare 阶段）和 binlog 各 fsync 一次，是 crash-safe 的标准配置；② 支撑高 TPS 靠组提交：多个并发事务的 redo log 以 LSN 为界，由组 leader 一次 fsync 带动整组落盘，组员越多省的 IOPS 越多；③ MySQL 还故意把 redo fsync 拖到 binlog write 之后，让 binlog 也能组提交（可用 binlog_group_commit_sync_delay/_no_delay_count 调节）；④ WAL 的高效正来自顺序写+组提交两点。

**Q：binlog cache 线程私有，redo log buffer 却全局共用，为什么这样设计？**

**A：** ① binlog 要求一个事务的日志连续不可拆分，必须攒齐整个事务后一次写出，所以每个线程要有独立 cache；② redo log 无此要求，事务执行中随时可写入全局 buffer，且能搭其他事务提交的便车一起 fsync；③ 若未提交事务 crash，其 binlog 还在 cache 未发给备库，redo log 丢了也不影响主备一致——从业务视角该事务等于没提交过。

**Q：IO 成为瓶颈时，有哪些调整日志刷盘的策略？各自风险是什么？**

**A：** ① 设置 binlog_group_commit_sync_delay 和 binlog_group_commit_sync_no_delay_count，故意攒批减少 fsync，只增加响应时间、不丢数据；② sync_binlog 调为 100~1000，风险是主机掉电丢最近 N 个事务的 binlog；③ innodb_flush_log_at_trx_commit 设为 2，风险是主机掉电丢数据，但 MySQL 进程重启不丢；④ 不建议设 0：redo log 只在内存，MySQL 自身异常重启就丢，且性能与 2 差别不大，收益低风险高。

**Q：从客户端视角，crash-safe 给出的是什么样的承诺？**

**A：** 三条语义：①收到"成功"，事务一定已持久化，redo 与 binlog 都已落盘；②收到"失败"，事务一定没有提交成功；③收到超时、断连等"不确定"结果，应重连后查询状态再决定重试还是放弃，不能盲目重发。数据库只负责自身内部一致（数据与日志、主备之间），"不确定就先查询"是应用层的职责，这个模型适用于几乎所有存储系统。

# MySQL实战45讲 面试题精选（24-29）

## 24 MySQL是怎么保证主备一致的？

**Q：简述主备同步的完整流程。**

**A：** ① 备库先 change master 指定主库地址、账号和同步起点（文件名+偏移量）；② start slave 后拉起 io_thread 和 sql_thread；③ 主库用专门线程响应备库长连接，按位点读取 binlog 发送；④ 备库 io_thread 收到后写入本地中转日志 relay log；⑤ sql_thread 解析 relay log 并执行。生产常用双 M 结构（两节点互为主备），切换时不用重建主备关系。

**Q：备库要同步数据，为什么还建议设置成只读 readonly？**

**A：** ① 防止运营类查询在备库误改数据；② 防止切换逻辑出 bug 造成双写、主备不一致；③ 可用 readonly 状态判断节点角色。只读不影响同步：readonly 对 super 权限无效，而负责回放日志的同步线程持有 super 权限。

**Q：binlog 的 statement、row、mixed 三种格式怎么对比选型？**

**A：** statement 记 SQL 原文，省空间，但像 delete 带 limit 这类语句，主备可能选不同索引删不同的行，有一致性风险；row 记每行的具体变更（Table_map + 行事件），保证一致，且便于误操作恢复（delete 转 insert、update 前后镜像对调），缺点是批量操作日志量大、IO 开销高；mixed 由 MySQL 自动判断，有风险就降级为 row。生产至少 mixed，主流做法是 row。

**Q：为什么不能用 mysqlbinlog 解析出的 SQL 直接拷贝执行来恢复数据？**

**A：** statement 格式的语句结果依赖上下文命令。例如 binlog 会额外记一条 SET TIMESTAMP=xxx 来固定 now() 的返回值；只把 insert 语句抠出来执行，时间函数取的是当前时间，恢复结果就错了。标准做法是把解析输出整段交给 MySQL 执行：mysqlbinlog master.000001 --start-position=... --stop-position=... | mysql ...

**Q：双 M 结构下如何避免循环复制？**

**A：** 靠 server id 判重：① 主备之间 server id 必须不同；② 备库回放 binlog 后生成的新 binlog 保留原事务的 server id；③ 节点收到日志先比对 server id，与自己相同说明是自己产生的，直接丢弃。于是 A 的更新传到 B 执行后，再带着 A 的 server id 传回 A 时被丢弃，死循环被切断。

**Q：server id 判重就一定不会循环复制了吗？**

**A：** 不一定。运行中把某节点的 server_id 改成与其他节点相同（set global），判重即刻失效；三节点级联迁移（如 B→A→A'）时，同一条日志可能带着原 server id 绕回生成它的节点，仍会循环。这类场景要主动调整 server id 或断开对应同步通道来切断环。理解"判重靠 server id"这个机制，才能推断它的漏洞在哪。

## 25 MySQL是怎么保证高可用的？

**Q：什么是主备延迟？seconds_behind_master 是怎么算的？**

**A：** 即同一事务在备库执行完成时刻减去主库执行完成时刻（T3-T1）。算法：取备库当前正在回放的事务在 binlog 中记录的主库写入时间，与备库系统时间相减。备库连主库时会用 UNIX_TIMESTAMP() 校准两边时钟差，所以主备机器时间不一致不影响结果。网络正常时，延迟主要来自备库回放 relay log 慢于主库生成 binlog。

**Q：主备延迟的常见来源有哪些？**

**A：** ① 备库机器性能差或多备库挤一台机器争抢资源——更新对 IOPS 的压力主备无差别，应同规格对称部署；② 备库压力大——分析类大查询占满 CPU，可一主多从分摊读、用 binlog 接外部系统；③ 大事务——主库事务提交才写 binlog，事务跑多久备库就延迟多久，如一次性删大量数据、大表 DDL；④ 备库并行复制能力不足。

**Q：对比可靠性优先与可用性优先两种主备切换策略。**

**A：** 可靠性优先：判断 SBM 足够小→主库置只读→等 SBM=0→备库放开读写→切流量；代价是中间一段双只读的不可写窗口，但数据不丢不冲突，推荐默认。可用性优先：不等同步直接切到备库并放开读写，几乎零不可用，但延迟期间两边各自写入会产生不一致；row 格式下冲突会报 duplicate key 暴露出来，mixed/statement 会悄悄不一致。仅当日志类写入可降级时才考虑可用性优先。

**Q：为什么说 MySQL 高可用系统的可用性取决于主备延迟？**

**A：** 主库故障后的被动切换，必须等备库把 relay log 全部回放（SBM=0）才能对外服务，否则客户端会短暂查不到已提交的事务，等于"数据丢失"，业务不可接受。因此延迟越大，故障恢复越慢，不可用时间越长；提升可用性的根本手段是把主备延迟压小。

## 26 备库为什么会延迟好几个小时？

**Q：为什么需要并行复制？整体模型是什么？**

**A：** 主库靠行锁支持高并发写入，而 5.6 之前备库 sql_thread 单线程回放，回放速度持续低于主库生成日志速度时，延迟会累积到小时级且追不上。所有并行方案都是把 sql_thread 拆成 coordinator（读 relay log 并分发）+ 多个 worker（真正执行），worker 数由 slave_parallel_workers 控制，32 核机器经验值 8~16，给读查询留资源。

**Q：coordinator 分发事务要满足哪两条原则？轮询分发为什么不行？**

**A：** ① 更新同一行（含同一唯一键）的事务必须分到同一 worker，否则执行顺序可能颠倒、产生更新覆盖；② 同一事务不能拆到多个 worker，否则会暴露"更新了一半"的中间状态，破坏隔离性。轮询分发无法保证①：CPU 调度可能让后分到的事务先执行，同一行两个事务在主备上顺序相反，导致主备不一致。

**Q：对比按表、按行、按库三种并行分发策略。**

**A：** 按表：以"库名.表名"判冲突，实现简单，但热点表会退化成单线程；按行：以"库名+表名+唯一键值"判冲突，并行度更高，但要解析 binlog 算 hash，大事务耗 CPU/内存，需设阈值退化为单线程；按库（5.6 官方）：hash 只用库名，构造快且不要求 row 格式，但单库或库间热度不均就无效。前两者要求 binlog 为 row、表有主键、无外键。

**Q：MySQL 5.7 的 LOGICAL_CLOCK 和 WRITESET 并行策略核心思想是什么？**

**A：** LOGICAL_CLOCK：事务只要同时到达 redo log prepare 阶段，说明已通过锁冲突检验，即可在备库并行；还可调大 binlog_group_commit_sync_delay 等参数拉长组提交窗口，人为制造更多并行事务。WRITESET（5.7.22）：主库对每行按"库名+表名+索引名+值"算 hash 写入 binlog，备库按 writeset 无交集即并行，无需解析 binlog 行数据，省 CPU 内存，statement 格式也支持；表无主键或有外键则退化单线程。

**Q：MariaDB 的按组提交并行复制是什么思路？有什么缺陷？**

**A：** 把主库同一组提交（相同 commit_id）的事务分到一组在备库并行执行，相当于"模拟主库当时的并发"。缺陷：必须上一组全部执行完才能开始下一组，组里只要有一个大事务，整组都被拖住，延迟反而恶化。

**Q：WRITESET_SESSION 与 WRITESET 有什么区别？**

**A：** WRITESET_SESSION 在"writeset 无交集即可并行"的基础上，额外要求同一 session 的事务保持先后顺序。如果主库的写入集中在低并发 session（业务近乎单线程压入），备库的并行度会退化到接近单线程——并行复制的效果依赖主库本身的并发度。

## 27 主库出问题了，从库怎么办？

**Q：基于位点做一主多从切换，为什么位点难精确？怎么处理重复事务？**

**A：** 从库记的是原主库的位点，同一日志在新主库上位置不同，只能估算：等新主库 relay log 同步完→show master status 取最新位点→用 mysqlbinlog 按原主库故障时刻 T 定位。往前多取必然重放部分事务，常见报错 1062（唯一键冲突）、1032（删行不存在），可用 sql_slave_skip_counter 逐个跳过，或临时设 slave_skip_errors='1032,1062'，同步稳定后必须清掉，防止掩盖真正的不一致。

**Q：GTID 的格式与分配机制是什么？**

**A：** GTID=server_uuid:gno，事务提交时分配，是全局唯一标识（回滚不占号，因此序列连续）。gtid_next=automatic 时系统自动分配，随 binlog 记录并加入本实例 GTID 集合；手动指定 gtid_next 时，若该 GTID 已在集合中，对应事务会被直接忽略——这正是跳过重复事务的机制。开启需 gtid_mode=on 且 enforce_gtid_consistency=on。

**Q：GTID 模式下切换为什么简单？与位点协议的本质区别？**

**A：** change master 只写 master_auto_position=1，不用找位点。备库把自己的 GTID 集合发给主库，主库算差集（自己有、备库没有的），若本地 binlog 已被清理则直接报错拒绝，否则从第一个缺失事务起顺序发送。区别在于：位点协议由备库指定位置、主库不校验完整性；GTID 协议由主库保证日志完整、缺失即报错，找位点变成主库内部自动完成。

**Q：GTID 模式下如何用空事务跳过已执行的事务？**

**A：** 同步因某 GTID 已执行（如主键冲突）而停止时，手工提交空事务把它收进本实例集合：set gtid_next='uuid:gno'; begin; commit; set gtid_next=automatic; start slave; 之后从库再收到该 GTID 的事务会自动跳过。先在备库做在线 DDL、再让日志传回主库的场景，也用同样手法补齐 GTID 避免重复执行。

**Q：GTID 模式下需要的 binlog 已在主库被清理，从库怎么办？**

**A：** 从库先对比自己已执行的 GTID 集合与主库 gtid_purged（已清理区间），确认缺失段；若接受这段数据不一致，可在从库 reset master 后 set global gtid_purged=主库的清理集合，让从库"视为已执行过"，从第一个现存事务继续同步；不接受就只能重建从库，或从保留全量日志的中转从库补齐。

## 28 读写分离有哪些坑？

**Q：客户端直连与带 proxy 的读写分离架构怎么选？**

**A：** 客户端直连：少一跳转发、性能略好、架构简单易排查，但客户端感知后端细节，主备切换/迁移需改连接信息，一般配 Zookeeper 类组件管理后端。带 proxy：客户端只连代理、对业务友好，连接与后端信息维护由 proxy 承担，但 proxy 本身要高可用，整体更复杂。按数据库团队运维能力选择，趋势是 proxy 方向。

**Q：过期读是怎么产生的？**

**A：** 读写分离是"写主读从"，而主从复制延迟无法 100% 消除。客户端提交更新事务后立刻发起查询，若请求被路由到从库，从库可能还没回放该事务，读到的就是更新前的旧状态。这是读写分离架构的固有问题，必须在业务或中间件层面选择方案处理。

**Q：解决过期读有哪些方案？各自的适用与局限？**

**A：** ① 强制走主库：按"能否接受旧数据"给请求分类，必须最新的走主库，最常用，但金融类全走主库等于放弃扩展；② sleep：更新后睡 1 秒再读，或前端 Ajax 先回显，简单但不精确；③ 判断无延迟：SBM=0 或比对位点/GTID 集合，只保证"收到的都执行完"，不保证收全最新日志；④ semi-sync：主库等至少一个从库 ack 才返回提交，一主一从成立，一主多从查到未 ack 的从库仍会过期；⑤ 等位点/等 GTID：只等本次事务回放完成，精确且无过度等待。

**Q：等主库位点方案的流程是什么？**

**A：** ① 更新事务提交后，在主库 show master status 拿 File/Position；② 选一台从库执行 select master_pos_wait(File, Position, 1)；③ 返回>=0 表示该位置已回放，安全执行查询；④ 超时返回 -1 或异常返回 NULL 时，退化到主库查询。它把等待范围从"主备完全同步"缩小到"我关心的这个事务已执行"，避免持续延迟下的过度等待。

**Q：等 GTID 方案相比等位点方案好在哪？**

**A：** 等位点要额外查一次 show master status；GTID 方案把 session_track_gtids 设为 OWN_GTID，更新事务的返回包直接携带该事务 GTID（客户端通过 API mysql_session_track_get_first 解析），省一次往返。之后在从库执行 select wait_for_executed_gtid_set(gtid1, 1)，返回 0 表示已执行可查，超时返回 1 则退化去主库；从库全延迟时请求会涌向主库，需业务侧限流。

**Q：semi-sync（半同步复制）是为了解决什么问题？**

**A：** 异步复制下，主库提交即向客户端返回成功，若这一瞬主库掉电，binlog 还没传到从库，这些"已确认"的事务就永久丢了。semi-sync 要求主库等至少一个从库确认收到 binlog（ack）后才返回成功，把已确认事务的丢失风险挡住，常用于一致性要求高的核心业务；代价是每次提交多一次 RTT 等待。

## 29 如何判断一个数据库是不是出问题了？

**Q：用 select 1 做探活有什么缺陷？**

**A：** select 1 只能证明进程活着、网络通，不代表服务可用。当 innodb_thread_concurrency（建议 64~128）的并发查询额度被大查询占满时，新查询会全部堵在引擎外，而 select 1 这类不访问 InnoDB 的语句照样秒回，探活误报"健康"。所以必须用能触达 InnoDB 的检测手段。

**Q：并发连接和并发查询是一回事吗？锁等待算不算并发计数？**

**A：** 不是一回事。show processlist 里几千个是并发连接，只多占内存；真正耗 CPU 的是"正在执行"的并发查询，innodb_thread_concurrency 限制的是后者。进入锁等待的线程计数会减一：它已不占 CPU，且若不减，128 个线程等同一把行锁时计数被占满，持锁事务无法提交，整个系统会被锁死，所以这个设计必要且合理。

**Q：健康检测如何从 select 1 演进到更新判断？**

**A：** select 1 查不出 InnoDB 堵塞→改成查表 select * from mysql.health_check，能发现并发线程占满，但发现不了磁盘写满导致更新堵死（此时读仍正常）→再改成 update 检测表刷新时间戳。双 M 结构下主备都执行同一更新会冲突回传，所以用 server_id 做主键，insert ... on duplicate key update，各节点各写各的行，互不干扰。

**Q：更新检测为什么会"判定慢"？根因是什么？**

**A：** 检测靠超时 N 秒判定不可用。当日志盘 IO 利用率 100% 时业务已严重受损，但检测 update 资源需求极小，总能在 IO 队列里分到一点资源、在 N 秒内提交返回，HA 便误判系统正常。根因：外部检测靠定时轮询，有随机性和滞后性，且结论取决于检测语句自身的资源需求，可能持续误报正常。

**Q：如何用 performance_schema 做内部统计检测？**

**A：** MySQL 5.6+ 在 performance_schema.file_summary_by_event_name 按事件统计每次 IO 耗时：redo log 对应 wait/io/file/innodb/innodb_log_file，binlog 对应 wait/io/file/sql/binlog，含次数及 SUM/MIN/AVG/MAX 耗时（皮秒）。定时查询 MAX_TIMER_WAIT 超阈值（如 200ms）即判异常，处理后 truncate 清空统计重新累积。全开约损耗 10% 性能，建议只开需要的项；它是数据库内部视角，能发现外部轮询发现不了的问题。

## 30 答疑文章（二）：用动态的观点看加锁

**Q：InnoDB 的加锁规则可以怎么概括？**

**A：** 记成"两原则、两优化、一 bug"：①基本加锁单位是 next-key lock，即前开后闭区间；②只有查找过程中访问到的对象才加锁；③唯一索引等值查询时，next-key lock 退化为行锁；④等值查询向右遍历、最后一个值不满足条件时，退化为间隙锁；⑤bug：唯一索引上的范围查询会一直访问到第一个不满足条件的值为止。所有加锁范围分析都从这套规则出发。

**Q：where 条件写的是不等号，为什么说执行过程中也有"等值查询"？**

**A：** 加锁发生在执行过程中，必须结合索引的访问路径看。以 id>9 and id<12 order by id desc for update 为例：优化器先在 B+ 树上等值搜索 id=12，没找到，落在 (10,15) 间隙，按优化 2 退化为间隙锁；随后向左遍历，这一步不是等值查询，扫到 id=5，加 next-key lock (0,5]。可见"等值查询"指的是树搜索定位记录这个动作，与 SQL 写法无关，这就是"用动态的观点看加锁"。

**Q：间隙锁之间不冲突，为什么两条 select ... where c in(5,20,10) 还会死锁？**

**A：** 间隙锁互不排斥，但记录锁互斥，且锁是执行中逐个加的。普通顺序按 5→10→20 加三把记录锁；若加 order by c desc，则按 20→10→5 加。两条语句锁相同的三行、顺序相反，并发时可能各持有部分记录锁又互相等待，构成死锁。结论：①对同一组资源要按尽量一致的顺序访问；②死锁发生时 InnoDB 选择回滚undo更少、代价更小的事务（如 lock in share mode 那条）。

**Q：如何通过 show engine innodb status 分析死锁现场？**

**A：** 看 LATEST DETECTED DEADLOCK 一节：它分三个部分——两个 TRANSACTION 各自的信息，以及最终回滚了哪个事务。每个事务重点看两块：HOLDS THE LOCK(S) 表示当前持有哪些锁，WAITING FOR THIS LOCK TO BE GRANTED 表示在等哪把锁；其中 index/lock mode S or X waiting 说明锁所在索引和模式，hex 字段可还原出被锁记录的索引列和主键值。把两边的"持有+等待"拼起来就能还原死锁环路。

**Q：为什么说"间隙是由它右边的记录定义的"？这对分析锁有什么影响？**

**A：** 锁信息里 gap before rec 指的是某条记录之前的空隙。例如 (5,10)、(10,15) 分别由 c=10、c=15 定义；一旦 delete 掉 id=10，两个间隙合并为 (5,15)，原先他人持有的锁范围随之"变大"，之后向 (5,15) 内 insert 会因插入意向锁与间隙锁冲突被堵住。所以加锁范围不是语句执行完就固定的，数据增删会实时改变间隙边界，分析时要动态推演。

**Q：为什么 update 修改索引列的值，相当于"删除+插入"两个动作？**

**A：** 索引是按值有序的 B+ 树，值的改变意味着这条索引记录要从旧位置挪到新位置，InnoDB 的实现就是删旧位、插新位。推论：①update 改索引列可能被"新值所在位置"的间隙锁堵住，分析锁冲突要同时看新旧两个位置；②其他事务对这两个位置的插入/删除都会实时改变你已持有的锁范围，印证"用动态的观点看加锁"。

## 31 误删数据后除了跑路，还能怎么办？

**Q：误删了数据行，如何恢复？原理是什么？**

**A：** 用 Flashback 类工具闪回，前提是 binlog_format=row 且 binlog_row_image=FULL。原理是把 binlog event 反转重放：insert 的 Write_rows 改成 Delete_rows，delete 反之，update 则把修改前/后镜像对调；涉及多个事务时需按逆序重放。不建议直接在主库执行恢复：误操作后业务可能已基于错误数据继续修改，直接插回可能二次破坏，更稳妥的是先在临时库重放、确认后再回主库。

**Q：drop/truncate 误删表或库，为什么 Flashback 救不了？正确姿势是什么？**

**A：** 这三类 DDL 即使在 row 格式下，binlog 记录的仍是 statement（只有一条语句），没有行镜像可反转。只能走"全量备份+binlog 增量"：①用最近一次全量备份恢复临时库；②应用备份点之后的 binlog，遇到误操作语句用 --stop-position/--start-position 跳过（GTID 实例可先空跑该 GTID 占位，后续自动跳过）；③校验后迁回。加速技巧：把临时库挂到线上备库下，配合 replicate_do_table 只同步误删表并利用并行复制。

**Q：延迟复制备库解决什么问题？**

**A：** MySQL 5.6 引入，用 CHANGE MASTER TO MASTER_DELAY=N 让备库固定落后主库 N 秒。若误删在 N 秒内被发现，误操作尚未在延迟备库执行，此时 stop slave 并跳过该条语句，就能得到一份最多只差 N 秒的数据，把按天计的恢复窗口压缩到小时以内。适合核心业务，是"全量备份+日志恢复"提速的关键补充。

**Q：事前如何预防误删？rm 删掉实例数据怎么办？**

**A：** 预防优先：①账号分离——开发只给 DML 权限，不给 drop/truncate；DBA 日常用只读账号；②操作规范——删表前先改名为 _to_be_deleted 后缀观察一段时间，物理删除只能走管理系统且仅限带后缀的表；③设置 sql_safe_updates=on，拦截无 where 或 where 不走索引的 update/delete；④SQL 上线前审计，备份定期演练并跨机房/跨城市保存。rm 删单节点不必慌，HA 会切主，恢复该节点再入集群即可。

## 32 为什么还有kill不掉的语句？

**Q：kill query/connection 的实现机制是什么？**

**A：** kill 并不强行杀死线程，只做两件事：把目标线程状态置为 THD::KILL_QUERY（kill connection 则置 KILL_CONNECTION 并关闭其网络连接），再给线程发一个信号把它从可唤醒的等待中拉起来。真正的终止要等线程执行到语句中预埋的检查点、发现状态被标记后，才进入终止逻辑并释放 MDL 锁等资源。这和 Linux 的信号机制类似：发信号不等于进程立即退出。

**Q：哪些情况下 kill 会无效或迟迟不生效？**

**A：** 两类原因：①线程到不了检查点——如等 innodb_thread_concurrency 名额时是"每 10ms 试一次然后 nanosleep"的循环，不检查线程状态，kill 的信号也唤不醒它；IO 压力过大导致读写函数长时间不返回同理。②终止逻辑本身很慢——大事务回滚要回收大量数据版本，大查询/DDL 被杀后要删大临时文件，都受 IO 制约。此时只能改善环境（调大并发参数、降低系统压力）等它自己结束，无法再强杀。

**Q：show processlist 中 Command=Killed 代表什么？**

**A：** 这是 show processlist 的特殊显示规则：只要线程状态是 KILL_CONNECTION，Command 列就显示为 Killed。它不代表线程已退出——客户端可能已经收到断连提示，但服务端语句仍在等待或回滚中，直到线程走到检查点并完成整个终止逻辑，该线程才会真正消失。

**Q：客户端 Ctrl+C 能停掉慢查询吗？连接慢是因为库里表太多吗？**

**A：** 都是误解。①客户端操作不了服务端线程，Ctrl+C 实际是新开连接发一条 kill query，服务端仍可能停不下来；MySQL 是停等协议，同一连接里再发命令也没用。②连接慢不是服务端慢，是客户端默认开启库名/表名自动补全：连上后执行 show databases/tables 并在本地构建哈希表，表多就卡住，加 -A 关闭即可。另外 --quick(-q) 让客户端改用读一行处理一行的 mysql_use_result 方式，省本地内存，但客户端处理慢会反压服务端。

**Q：kill 大事务后回滚很慢，重启实例能跳过回滚吗？**

**A：** 不能，反而更糟。崩溃恢复时 InnoDB 必须把没做完的回滚继续做完，重启绕不过这一步；且回滚与正常流量抢资源，恢复期整体更慢。正确做法是让它自己回滚完；期间影响业务就先做主备切换，回头再等旧实例慢慢恢复。

## 33 我查这么多数据，会不会把数据库内存打爆？

**Q：对 200G 的大表做全表扫描，为什么不会打爆服务端内存？**

**A：** 因为 MySQL 是"边读边发"：执行器取一行写入 net_buffer（默认约 16K），写满就发往客户端，发送成功即清空继续取；若客户端网络栈写满（返回 EAGAIN/WSAEWOULDBLOCK），服务端暂停等待。所以保存结果集占用的内存上限约为 net_buffer_length，与表大小无关；客户端读得慢只会拉长语句执行时间（State 显示 Sending to client），不会 OOM。逻辑备份整库扫描同理。

**Q：Sending to client 和 Sending data 有何区别？**

**A：** 易混状态，含义完全不同。①Sending to client：专指服务端 socket send buffer 写满、正在等客户端取结果，大量出现要督促业务优化返回数据量，或临时调大 net_buffer_length 缓解。②Sending data：语句进入执行阶段后就被设置，表示"执行器正在执行"，可能是锁等待、扫描等任意阶段，与网络无关。看到 Sending data 居多，别误判成网络问题，要结合锁和执行计划分析。

**Q：标准 LRU 处理全表扫描有什么问题？InnoDB 如何改进？**

**A：** 若按朴素 LRU，冷数据全表扫描会把 Buffer Pool 中的热页全部淘汰，命中率骤降、磁盘压力飙升。InnoDB 把 LRU 链表按 5:3 分为 young 和 old 两区：新读入的页先插到 old 区头部；old 区的页需要再次被访问、且在链表中已停留超过 1 秒（innodb_old_blocks_time 默认 1000ms）才晋升 young 区。顺序扫描时同一页首末次访问间隔通常不足 1 秒，会一直留在 old 区被快速淘汰，从而保护正常业务的命中率（线上要求 99% 以上）。

**Q：Buffer Pool 的作用与大小如何设置？**

**A：** 两大作用：①配合 redo log 实现 WAL，把随机写盘转为顺序写，加速更新；②缓存最新数据页加速查询——事务提交后磁盘页是旧的，但读请求直接命中内存最新版本，无需先应用 redo。大小由 innodb_buffer_pool_size 决定，通常设为物理内存的 60%~80%；命中率用 show engine innodb status 中的 Buffer pool hit rate 观察。

## 34 到底可不可以使用join？

**Q：Index Nested-Loop Join（NLJ）是怎么执行的，性能如何？**

**A：** 当 join 字段能用上被驱动表索引时走 NLJ：从驱动表读一行，取出关联字段值到被驱动表做树搜索，命中则拼成结果行，循环到驱动表末尾。总成本近似 N + N*2*log2M（N、M 分别为驱动表、被驱动表行数），两个 100 行的小表 join 只扫约 200 行。相比在应用层拆成 1+N 条 SQL 再拼接结果，join 少了 N 次网络交互和客户端拼装逻辑，所以"能用上索引的 join 放心用"。

**Q：被驱动表没有可用索引时走什么算法？**

**A：** MySQL 放弃了逐行全表扫描的 Simple Nested-Loop Join，改用 Block Nested-Loop Join（BNL）：把驱动表的 join 相关数据分批装入 join_buffer（默认 256K），再全表扫描被驱动表，每行与 buffer 中所有行在内存中比对，满足条件即输出。总扫描行数 M+N，比较次数 M*N；buffer 不够就分段，被驱动表被多扫几遍。它省掉的是随机读，代价是 CPU 大量比较和可能反复扫描大表。

**Q：到底能不能使用 join？如何判断？**

**A：** 标准看 explain 的 Extra 字段：①没有 Block Nested Loop 字样，说明用上了被驱动表索引走 NLJ，可以用，且比拆成多条单表 SQL 更好；②出现 Block Nested Loop，说明走 BNL，大表 join 扫描行数和内存比较次数都会爆炸，尽量不要用，应先给被驱动表的关联字段补索引，把 BNL 转成 NLJ/BKA。

**Q：为什么要"小表驱动大表"？这里的"小表"指什么？**

**A：** NLJ 成本 N + N*2*log2M 中，驱动表行数 N 是乘在外面的系数：N 扩大 1000 倍成本涨 1000 倍，M 扩大 1000 倍只涨不到 10 倍，所以让小表驱动。BNL 在 buffer 足够大时大小表等价，不够大时也是小表更省扫描，故结论统一为"总是小表驱动"。注意"小表"≠行数少：应按各自 where 过滤后，比较实际参与 join 的字段总数据量，量小的才算小表——可能行数更少，也可能是只需取一列的那个表。

## 35 join语句怎么优化？

**Q：什么是 Multi-Range Read（MRR）优化？为什么能提速？**

**A：** 普通索引范围查询回表时，拿到的主键 id 随索引序递增而乱序，逐个回主键树就是随机读。MRR 的做法：①把查到的 id 先放入 read_rnd_buffer；②在 buffer 内对 id 排序；③按主键递增顺序回表，使磁盘读接近顺序读。它只在多值/范围查询（能收集到足够多 id）时收益明显。稳定启用需 set optimizer_switch='mrr=on,mrr_cost_based=off'，explain 的 Extra 出现 Using MRR。

**Q：BKA 算法是什么？与 NLJ、MRR 什么关系？**

**A：** Batched Key Access 是对 NLJ 的优化。NLJ 每次只把一个关联值传给被驱动表，MRR 的排序优势用不上；BKA 复用 join_buffer，一次从驱动表取一批行传给被驱动表，再借助 MRR 把主键排序后批量回表。由于依赖 MRR，启用要设 optimizer_switch='mrr=on,mrr_cost_based=off,batched_key_access=on'；buffer 放不下时分批执行。MySQL 已内置该优化，建议默认使用。

**Q：BNL 有哪些危害？如何优化？**

**A：** 三大危害：①对被驱动表反复全表扫描，占用大量 IO；②join 比较次数为 M*N，大表时 CPU 消耗巨大；③扫描冷表且语句超过 1 秒时，冷表数据页会被提升进 LRU young 区，挤掉正常业务热页，Buffer Pool 命中率持续受损（IO 影响语句结束即止，这个影响是持续性的）。优化方向是让被驱动表用上索引：能建索引直接建；对低频、过滤后数据量很小的场景建索引不划算，可先把过滤结果写入带索引的临时表，再与临时表 join，即"BNL 转 BKA"。

**Q：当时 MySQL 不支持 hash join，应用端如何自己实现等价优化？**

**A：** 思路是把 M*N 次比较改成哈希查找：①select 驱动表（过滤后的小结果集），在业务端放入 hash 结构（如各语言的 map/set）；②select 被驱动表中满足条件的行；③逐行到 hash 表中匹配，命中即拼接输出。总操作量降为 M+N 级，理论性能优于临时表方案。文中例子：10 亿次比较的 BNL join，改用"临时表+索引"后总耗时从 1 分 11 秒降到 1 秒内，hash join 可更快（MySQL 8.0.18 起已原生支持）。

# MySQL实战45讲 面试题精选（36-41）

## 36 为什么临时表可以重名？

**Q：临时表和内存表是一回事吗？**

**A：** 不是，是两个维度的概念。①内存表指 Memory 引擎的普通表，数据全在内存、重启清空但表结构保留，对所有会话可见；②临时表用 create temporary table 创建，可用任意引擎，InnoDB 临时表数据同样落盘；③临时表只对创建它的会话可见，show tables 看不到，会话结束自动删除。同名时同会话内增删改查优先命中临时表。

**Q：为什么不同会话可以创建同名的临时表？**

**A：** ①磁盘层：5.6 及之前临时表落盘为 tmpdir 下以"#sql+进程id+线程id+序号"为前缀的文件，天然不重名（5.7 起 InnoDB 用户临时表改存独立的临时表空间）；②内存层：每张表靠 table_def_key 区分，普通表由"库名+表名"生成，临时表额外拼入 server_id 和 thread_id，故同名临时表 key 不同；③每个线程维护自己的临时表链表，会话内操作先查链表，命中则优先操作临时表，会话结束时逐个执行 DROP TEMPORARY TABLE 自动清理。

**Q：为什么临时表特别适合 join 优化、分库分表跨库汇总这类场景？**

**A：** 两点核心优势：①不同会话的临时表可重名，多个会话并发执行同一段处理逻辑不会因表名冲突而建表失败；②会话异常断开或实例重启时自动回收，省去清理中间表的收尾逻辑。分库分表跨库查询中，可把各分库的查询结果先插入汇总库的临时表，再在临时表上统一做排序、聚合，避免在 proxy 层实现复杂的计算逻辑。

**Q：statement 格式下临时表操作为什么要写 binlog？备库同名临时表为何不冲突？**

**A：** 备库重放时也需要这些临时表（如 insert...select 依赖它），否则报"表不存在"、同步中断；且备库 apply 线程常驻，不会像主库线程退出那样自动删表，所以必须显式记录 DROP TEMPORARY TABLE。备库靠 binlog 中记录的主库 thread_id 构造 table_def_key，主库两个会话的同名临时表在备库仍是两个不同对象。row 格式下临时表操作完全不记 binlog。

**Q：drop table 语句写入 binlog 时会发生什么变化？**

**A：** 服务端会改写这条语句：剔除其中引用的临时表，并在语句后追加 /* generated by server */ 注释。否则备库回放时找不到同名临时表会报"表不存在"、同步中断。因此 binlog 里的 drop table 可能和客户端原句不完全一样，做日志审计或数据恢复时要留意。

## 37 什么时候会使用内部临时表？

**Q：union 为什么用临时表，union all 为什么不用？**

**A：** union 语义要求合并后去重。执行时建一个内存临时表，分组结果字段上带主键/唯一约束，把各子查询结果逐行往里插，插到重复行时违反唯一约束而失败，以此实现去重，最后读出临时表返回。union all 不去重，子查询依次执行、结果直接发给客户端，无需暂存中间结果，explain 中也不会出现 Using temporary。

**Q：group by 为什么需要临时表？执行流程是怎样的？**

**A：** 因为扫描时分组列的值是无序到达的，需要一个带唯一键的结构边扫边累计。①建内存临时表，分组列做唯一主键，另设计数字段；②逐行计算分组值：不存在则插入计数 1，已存在则计数加 1；③扫完后按分组列排序返回结果。若数据量超过 tmp_table_size（默认 16M），内存临时表转磁盘临时表（默认 InnoDB），代价显著上升。

**Q：如何优化 group by，消除 Using temporary 和 Using filesort？**

**A：** 核心思路是让输入有序：分组值有序时只需顺序扫描、同值累加，扫完即得结果，无需临时表和排序。①优先给分组列建索引（5.7+ 可用生成列+索引适配表达式分组，如 id%100）；②确定数据量大且用不上索引时，加 SQL_BIG_RESULT 提示，让优化器跳过内存临时表，直接用 sort_buffer 排成有序数组再统计；③结果不需要排序时加 order by null，省掉最后一步排序。

**Q：sort_buffer、join_buffer、临时表如何区分和选择？**

**A：** 看执行逻辑需要的数据结构：join_buffer 是无序数组，用于被驱动表批量匹配；sort_buffer 是可排序数组，用于排序；临时表是二维表结构，支持唯一性约束和多字段存储，当逻辑必须用这些特性时启用——union 去重靠主键约束，group by 靠唯一键+计数字段。若语句能边读数据边直接产出结果，三者都不需要。

## 38 都说InnoDB好，那还要不要使用Memory引擎？

**Q：InnoDB 索引组织表和 Memory 堆组织表的本质区别是什么？**

**A：** ①InnoDB 数据直接放在主键索引 B+ 树上，二级索引存主键值，称索引组织表，数据按主键有序，普通索引查询要两次查找；②Memory 引擎数据按写入顺序存于数组，所有索引只存数据位置指针，称堆组织表，各索引地位相同。因此 Memory 有空洞时找空位即插，InnoDB 必须按主键序写入；Memory 不支持 Blob/Text，varchar 也按定长 char 存储。

**Q：为什么内存表的主键无法支持范围查询？如何解决？**

**A：** Memory 引擎主键默认是 hash 索引，key 无序，等值查找快但范围条件（如 where id<5）完全用不上，只能顺序扫数组。解决方法是显式建 B-Tree 索引：alter table t add index idx using btree(id)，之后范围查询优化器会自动选择它。这也说明内存表适合等值点查场景，不适合范围分析型查询。

**Q：生产环境为什么不建议用 Memory 引擎存业务数据？**

**A：** 两个硬伤：①只支持表锁不支持行锁，一个更新会阻塞全表所有读写，并发更新能力差；②重启数据全部丢失，主从架构下危害放大——备库重启清空后 apply 线程 update 报"找不到行"导致同步停止；双 M 架构下实例重启还会向 binlog 写 DELETE FROM 表并同步到对端，把对方内存表数据也删掉。而读多量小的表用 InnoDB，数据也能全量缓存在 Buffer Pool，性能并不差。

**Q：什么场景下内存表反而是好选择？**

**A：** 用户临时表场景。数据量可控时建 engine=memory 的临时表：①临时表仅本会话可见，无并发锁竞争，绕开表锁短板；②会话结束即删，重启丢数据无影响；③不参与主备复制的业务读写。相比 InnoDB 临时表，写内存不落盘更快，且可对 join 字段用 hash 索引加速等值匹配，是复杂查询优化的利器。

## 39 自增主键为什么不是连续的？

**Q：自增值存在哪里？实例重启后会变吗？**

**A：** 分引擎：MyISAM 存在数据文件中；InnoDB 5.7 及之前只存内存，重启后第一次打开表时取 max(id)+1 作为自增值——若删过最大 id 行再重启，自增值会回退；8.0 起把自增值变更写入 redo log，实现持久化，重启后恢复为重启前的值。注意自增值并不存在表结构文件里，show create table 显示的 AUTO_INCREMENT 只是当前值的快照。

**Q：哪些情况会导致自增主键出现空洞？**

**A：** 三类原因：①唯一键冲突——自增值在真正插入前就加 1，插入失败也不回退，如申请到 id=2 后撞唯一键，下次直接从 3 开始；②事务回滚——已分配的 id 同样不回收；③批量插入的翻倍申请策略——insert...select 这类语句预知不了行数，按 1、2、4…的个数分批申请，用不完的浪费掉。此外显式插入大于当前自增值的 id，也会把自增值推高。

**Q：为什么唯一键冲突或回滚后，MySQL 不把自增值回退？**

**A：** 是性能与正确性的权衡。并发事务加锁顺序申请 id，若允许回退，会出现表中已存在更大 id 而自增值变小的状态，后续事务会申请到重复 id 报主键冲突。要规避只有两条路：每次申请前先查主键树确认 id 不存在，成本高；或把自增锁持有到事务结束，并发能力大降。InnoDB 干脆不回退，只保证 id 递增、不保证连续，业务不要依赖连续性做设计。

**Q：innodb_autoinc_lock_mode 各取值含义是什么？生产如何设置？**

**A：** 0：自增锁持有到语句结束才释放（5.0 老策略）；1（默认）：简单 insert 申请后立即释放，insert...select 等批量插入仍持语句级锁；2：所有申请都是拿完立即释放。批量插入持语句锁是为了 statement 格式 binlog 的主备一致——只有连续分配的 id 串行重放才能复现原库结果。生产推荐 mode=2 且 binlog_format=row：row 按行记录真实数据，不依赖自增连续性，可彻底放开并发。

**Q：auto_increment_offset 和 auto_increment_increment 有什么用？**

**A：** 二者共同决定自增值的生成：offset 是起点偏移，increment 是步长。经典用法是双 M 双写：两个库都设 increment=2，一个 offset=1 只产生奇数 id、另一个 offset=2 只产生偶数 id，两边生成的 id 天然错开，避免双写主键冲突。

**Q：innodb_autoinc_lock_mode=1 下，哪些 insert 能"算准个数、立即释放锁"？**

**A：** 普通的多 values insert 能精确知道要几个 id，申请完立刻释放自增锁；需要持有到语句结束的是那些"预知不了行数"的批量插入——insert...select、replace...select、load data。理解这一点就能判断并发插入会不会被自增锁串行化。

## 40 insert语句的锁为什么这么多？

**Q：可重复读下 insert...select 为什么要给源表加锁？**

**A：** 为了 statement 格式 binlog 的主备一致。若不加锁，并发下可能出现事务先插入源表、却后写 binlog 的乱序，备库串行重放时这行会被 insert...select 一并带进目标表，与主库不一致。因此 RR + statement 时，该语句会对源表扫描到的记录和间隙加共享 next-key lock，期间其他事务不能插入源表。改用 row 格式即可避免这类锁。

**Q：insert 和 select 作用同一张表会有什么问题？如何优化？**

**A：** 存在循环写入：一边遍历一边向同表插入，直接写回可能在遍历中读到刚插入的行、参与计算后违背语义，所以 MySQL 用临时表中转数据。代价是 limit 1 无法在子查询中下推，导致对原表全表扫描，并给所有间隙加共享 next-key lock，阻塞其他插入。优化：先把子查询结果写入内存临时表，再从临时表取数插入原表，扫描行数从全表降为 1。

**Q：insert 唯一键冲突为什么会引发死锁？**

**A：** 冲突时 insert 不只是报错，还会在冲突的唯一值上申请共享 next-key lock（S 锁）。经典死锁链：事务 A 插入成功持有该值的排他锁；B、C 并发插入同值，冲突后各自加到 S 锁等待；A 回滚释放写锁后，B、C 都要升级为写锁继续插入，互等对方的 S 锁，形成死锁。实践上捕获唯一键冲突后应尽快提交或回滚事务，缩短持锁窗口。

**Q：insert ... on duplicate key update 有哪些注意点？**

**A：** 语义是插入冲突时转为执行 update；加锁为冲突索引上的排他 next-key lock，比普通冲突的共享锁更重。①多个唯一索引同时冲突时，按索引定义顺序只更新第一个冲突的行；②affected rows 有迷惑性：真插入返回 1，走更新返回 2（insert 与 update 计数各加 1），实际只改一行，做幂等/影响行数判断时不要误读。

## 41 怎么最快地复制一张表？

**Q：用 mysqldump 导出导入数据有哪些关键参数和注意点？**

**A：** ①--single-transaction 用一致性快照导出，避免锁表（InnoDB）；②--no-create-info 不导建表语句；③--set-gtid-purged=OFF 不带 GTID 信息；④--add-locks=0 输出不加 LOCK TABLES；⑤--where 支持按条件导部分数据。产出为多条 value 合并的 INSERT，回放快。注意 source 是客户端命令，服务端真正执行的是文件里的 INSERT 语句，binlog 与慢日志记录的也是这些语句。

**Q：select ... into outfile + load data 的流程和注意事项？**

**A：** outfile 把结果写到服务端文件：路径受 secure_file_priv 限制、不能覆盖同名文件、字段内换行制表符会被转义。load data 校验每行字段数后写入，整体一个事务。statement 格式下主库把文件内容直接写进 binlog，备库先落本地临时文件、再执行带 local 的 load data，主备可正常同步；local 表示读客户端文件，不加则读服务端文件。缺点是不导表结构、一次只能一张表。

**Q：直接拷贝表的 .frm/.ibd 文件可行吗？正确做法是什么？**

**A：** 直接拷贝不行：InnoDB 表除物理文件外还必须在数据字典中注册，目标库里没有对应表信息，系统不识别。正确姿势是 5.6 引入的可传输表空间：create table r like t → alter table r discard tablespace → flush table t for export（生成 cfg）→ 拷贝 cfg 和 ibd → unlock tables → alter table r import tablespace。注意 flush 后源表只读直到 unlock；import 需逐页改表空间 id，大文件也远快于逻辑导入。

**Q：三种复制表的方法如何选型？**

**A：** ①物理拷贝（可传输表空间）最快，适合大表复制与误删表恢复，但只能整表、需登录服务器、仅限 InnoDB 对 InnoDB；②mysqldump 可带 where 导部分数据，但 where 不支持 join 等复杂写法；③outfile/load data 最灵活、任意 SQL 均可，但一次一张表、表结构需单独导出。后两者是逻辑方式，可跨引擎；小数据量或需过滤用逻辑导出，大表追速度用物理拷贝。

**Q：secure_file_priv 如何限制 outfile/load data？**

**A：** 三种取值三种效果：①设为某个目录——读写只能发生在该目录及其子目录下；②NULL——禁止 outfile 导出；③空串——不限制，但不安全，生产不建议。遇到 "The MySQL server is running with the --secure-file-priv option" 报错时，先 show variables like 'secure_file_priv' 确认可用目录。

# MySQL实战45讲 面试题精选（42-结束语）

## 42 grant之后要跟着flush privileges吗？

**Q：grant 之后需要执行 flush privileges 才能生效吗？两者的底层机制分别是什么？**

**A：** 不需要。权限数据同时存在于磁盘系统表和内存结构中：①全局权限存于 mysql.user 表，内存对应 acl_users 数组；②库级权限存于 mysql.db 表，内存对应 acl_dbs 数组；③表/列权限存于 tables_priv、columns_priv 表，内存对应 column_priv_hash。grant/revoke 执行时会同步更新磁盘表和内存结构，权限判断用的是内存数据，所以赋权/收权即时生效，无需 flush。

**Q：grant 或 revoke 对已经存在的连接有什么影响？**

**A：** 要区分权限级别：①全局权限在线程对象里，登录时从内存数组拷贝一份到线程，之后 revoke 不影响已有连接，旧连接仍保留 super 等权限直到断开；②库/表/列权限的内存结构是全局共享的，每次判断都实时查，revoke 立刻对已有连接生效。注意一个细节：会话 use 某库时取得的库权限会存在会话变量里，切出该库前一直有效。

**Q：flush privileges 的正确使用场景是什么？**

**A：** 它的作用是清空内存权限数组，以磁盘系统表为准重新加载，用于修复两者不一致的状态。不一致通常源于不规范操作——直接用 DML 改系统权限表，比如 delete 掉 mysql.user 里的一行后，内存里用户仍在（还能登录），而 grant 又因表里没这行而失败，重建用户也报"已存在"，只有 flush 才能恢复一致。根本建议是：永远用 grant/revoke 管理权限，不要直接改系统表，flush 也就用不上了。

**Q：grant 赋权时有哪些常见的错误写法或误区？**

**A：** ①grant 后习惯性加 flush privileges——没必要，是老文档流传的误用；②用 `grant super on *.* to 'ua'@'%' identified by 'pa'` 一条语句赋权——identified by 会在用户不存在时创建用户、存在时直接改密码，很容易误改密码；应先 create user 再 grant；③给用户 all privileges 却允许所有 host 访问，权限范围失控；④误以为 user+密码标识用户，实际 user+host 才唯一确定一个用户。

## 43 要不要使用分区表？

**Q：分区表在 Server 层和引擎层分别是什么形态？这个差异带来什么行为？**

**A：** 分区表对 Server 层是一个逻辑表，对引擎层（如 InnoDB）则是多个独立的表（每个分区一个 .ibd 文件）。由此产生两个关键行为：①引擎层的锁是分区级别的，比如间隙锁、MyISAM 表锁只作用于命中的分区，其他分区不受影响；②Server 层所有分区共用一个 MDL 锁，DDL 时一个查询堵住会影响整个表，比手工分表的冲突面更大。查询时根据 where 条件与分区规则做分区裁剪，只访问必要分区。

**Q：为什么很多公司规范禁止使用分区表？**

**A：** 主要两个硬伤：①打开表行为——第一次访问分区表时要访问所有分区，MyISAM 的通用分区策略由 Server 层管理文件，分区数超过 open_files_limit 就直接报错；②共用 MDL 锁——任一分区上的语句都会持有整表 MDL 锁，DDL 影响被放大。8.0 起只允许实现本地分区策略的引擎（InnoDB、NDB），InnoDB 自己管理分区打开行为，问题有缓解，但 MDL 锁问题和跨分区查询开销仍在，所以有成熟分库分表中间件的团队多选业务分表。

**Q：分区表和手工分表的本质区别是什么？**

**A：** 引擎层看两者几乎等价：都是物理上多张表，性能没有实质差别。核心区别在路由位置：①分区表由 Server 层根据分区规则自动路由，SQL 对业务透明，代码简洁；②手工分表由应用层代码决定操作哪张分表，需要中间件或自己封装。此外运维差异明显：分区表 drop partition 可以秒级删除历史数据（直接删文件），手工分表则要整表 drop 或按表归档，但分区表 DDL 的 MDL 锁影响面更大。

**Q：分区表适合什么场景？使用时有哪些实践建议？**

**A：** 最典型场景是时序数据按时间清理历史：按时间分区后用 `alter table t drop partition ...` 直接删分区文件，比 delete 快且对系统影响小。实践建议：①分区不是越细越好，单表/单分区千万行在当前硬件下算小表；②不要提前预留大量分区，按月分区就年底再建下一年 12 个；③及时 drop 空的历史分区；④查询条件尽量带分区键，否则会扫描所有分区；⑤已有成熟分表中间件时优先业务分表。

**Q：分区表的主键有什么限制？如何设计自增主键？**

**A：** MySQL 要求分区表的主键（包括唯一键）必须包含全部分区字段，因此只能建联合主键。以按 ftime 分区为例：推荐 `PRIMARY KEY(ftime, id)`——因为分区键 ftime 出现在大多数查询条件里，联合主键可兼作前缀索引，省掉单独索引；InnoDB 还要求有以最左列开头的索引，需补一个 `KEY(id)`。反过来建 (id, ftime) 也可以，但要额外为 ftime 建索引，利用率更低。

## 44 答疑文章（三）：说一说这些好问题

**Q：left join 左边的表一定是驱动表吗？join 条件写 on 和写 where 有区别吗？**

**A：** 不一定，关键看条件写在哪：①left join 且被驱动表字段只出现在 on 里，语义保留"左表全量+右表补 NULL"，左表是驱动表；②若把被驱动表字段放 where 做等值判断，NULL 行会被过滤，语义退化为普通 join，优化器会改写并按索引选择驱动表（可用 show warnings 看到），此时左表可能变成被驱动表；③inner join 下 on 和 where 等价，优化器统一改写，执行计划完全相同。结论：需要 left join 语义时，被驱动表的过滤条件必须写在 on 里。

**Q：BNL 和 Simple Nested Loop Join 都是 M×N 次判断，为什么性能差很多？**

**A：** ①Simple NLJ 每轮都到被驱动表做全表扫描：数据不在 Buffer Pool 就要等磁盘读，还因反复访问把冷数据页顶到 LRU 链表头部，破坏正常业务的缓存命中率；②BNL 把驱动表数据一次性装入 join_buffer，被驱动表只做一次全表扫描，内存中与数组逐行比对，数组顺序遍历成本远低于反复的索引/指针查找。所以即使判断次数相同，BNL 的 IO 次数和 CPU 开销都小得多。

**Q：只要去重不聚合时，distinct 和 group by 哪个快？**

**A：** 性能相同。`select a from t group by a order by null` 去掉聚合函数后，语义就是"相同 a 值只返回一行"，与 distinct 完全一致，因此优化后执行流程也一样：①建一个带唯一索引的内存临时表（放不下则落磁盘临时表）；②遍历扫描表 t，逐行插入临时表，唯一键冲突就跳过；③遍历完把临时表作为结果返回。若字段 a 上有索引，两者都能走索引避免临时表，效率才真正提升。

**Q：statement 格式 binlog 下，主库两个事务获取自增 id 的顺序与写 binlog 顺序相反，备库重放会主键错乱吗？**

**A：** 不会。statement 格式下每个 insert 语句写入 binlog 时，前面都会带一条 `SET INSERT_ID=N`，显式指定该语句要用的自增值。即使主库上事务 A 拿 id=1、事务 B 拿 id=2，但提交顺序是 B 先 A 后，binlog 里记录的也是"SET INSERT_ID=2; 语句B; SET INSERT_ID=1; 语句A"，备库按序重放后各自 id 与主库一致。这也是 row 格式不需要该机制的原因——row 事件直接记录每行完整字段值。


**Q：NULL 的比较规则是什么？它如何让 left join 退化成 inner join？**

**A：** NULL 与任何值比较（包括 NULL=NULL、NULL!=0）结果都是 NULL，而 where/on 子句只保留结果为 true 的行。所以把"被驱动表的过滤条件"写到 where 里时，未匹配行（被驱动表字段全为 NULL）判断结果为 NULL，直接被过滤掉，left join 就退化成了 inner join；想保留 left join 语义，被驱动表的过滤条件必须写在 on 里。
## 45 自增id用完怎么办？

**Q：表定义的自增主键 id 达到上限后会发生什么？如何规避？**

**A：** 自增 id 达到类型上限（如 int unsigned 的 2^32-1）后再申请，值保持不变，下一次插入拿到相同 id，报 Duplicate entry 主键冲突，之后所有插入都失败，表变成只可读不可写。规避方法：①建表时评估数据量，有耗尽风险的表（高频插入删除）直接用 bigint unsigned；②int 上限约 42.9 亿，高写入场景并不遥远。注意报主键冲突是"插入失败"，影响可用性，数据本身不丢。

**Q：InnoDB 无主键表的 row_id 用完会怎样？为什么由此强调必须有显式主键？**

**A：** 无主键时 InnoDB 分配 6 字节不可见 row_id，上限 2^48-1。达到上限后归 0 循环递增，且新行会直接覆盖表中 row_id 相同的旧行——这意味着老数据被静默覆盖，数据丢失。对比：表自增 id 耗尽报主键冲突，只损失可用性；row_id 循环覆盖损失的是可靠性，而可靠性优先于可用性。所以 InnoDB 表应主动建自增主键，避免依赖系统 row_id。

**Q：Xid 和 InnoDB 的 trx_id 有什么区别？各自如何生成？**

**A：** 两者易混但层次不同：①Xid 由 Server 层维护，取自 global_query_id（纯内存变量，重启清零），用于关联 Server 与 InnoDB 的事务，binlog 中可看到；因重启清零，同一 binlog 文件内 Xid 唯一，跨文件可重复。②trx_id 是 InnoDB 内部事务 id，来自全局 max_trx_id（持久化，重启不清零），用于 MVCC 可见性判断——行数据记录 trx_id，与一致性视图对比判断可见。一个是跨层关联标识，一个是可见性核心。

**Q：为什么只读事务不分配 trx_id？innodb_trx 里查到的超大 trx_id 是什么？**

**A：** 两个好处：①减小一致性视图中活跃事务数组的大小——只读事务不影响可见性判断，构建视图时只需拷贝读写事务的 id；②普通 select 也对应只读事务，免申请 trx_id 大幅减少高并发下的锁冲突，同时减缓 trx_id 消耗速度。查到的大数是显示值：把事务 trx 变量的指针地址转整数再加 2^48，保证同一只读事务多次查询结果一致、并发只读事务互不相同，且与真实 trx_id 区分开。

**Q：max_trx_id 达到上限会出现什么问题？thread_id 为什么能做到不重复？**

**A：** max_trx_id 持久化、重启不清零，达到 2^48-1 后归 0 继续递增，会出现持续脏读：旧数据版本 trx_id 大于新写入版本的 0，被误判为可见。按 50 万 TPS 估算约 17.8 年触发，理论风险但真实存在。thread_id 则处理得最好：thread_id_counter 达 2^32-1 归 0 后，分配时用唯一集合插入失败就重取（do-while + insert_unique），保证 show processlist 里永远不出现重复的 thread_id。

**Q：select...for update 算只读事务吗？**

**A：** 不算。它属于当前读并申请了锁，InnoDB 会为其分配 trx_id，与普通读写事务一样受 trx_id 体系约束（包括 max_trx_id 用完的边界问题）。判断一个事务是否"只读"要看是否分配 trx_id，而不是看语句有没有写数据。
